# Kipet WoW Analyzer — архитектура проекта

Архитектура v1.0

30 октября 2026 · World of Warcraft Retail

Kipet WoW Analyzer — публичная веб-платформа для комплексного анализа персонажей, экипировки, талантов, боевой эффективности, Mythic+, рейдов и гильдий World of Warcraft.

Цель — создать не просто просмотрщик персонажей, а инструмент, который объясняет, что можно улучшить, почему это важно и на основании каких данных сделан вывод.

### Важные ограничения источников

1. Blizzard API будет главным источником профилей, характеристик, экипировки, талантов и гильдий. Данные персонажа могут обновляться после выхода игрока из игры, поэтому мы не обещаем актуальность в реальном времени.&#x20;

   [image](https://www.google.com/s2/favicons?domain=https://us.forums.blizzard.com\&sz=32)

   Blizzard Forums+1

2. Warcraft Logs API v2 позволит анализировать опубликованные боевые отчёты через GraphQL и серверную авторизацию приложения. Приватные отчёты без разрешения владельца не используются.&#x20;

   [image](https://www.google.com/s2/favicons?domain=https://www.warcraftlogs.com\&sz=32)

   Combat Analysis for Warcraft+1

3. Raider.IO технически предоставляет данные Mythic+ и рейдов, однако его условия запрещают создание конкурирующих сервисов на основе этого API. Поэтому интеграцию сделаем необязательной и отключённой до подтверждения допустимости использования. Сервис должен работать и без неё.&#x20;

   [image](https://www.google.com/s2/favicons?domain=https://raider.io\&sz=32)

### Почему не микросервисы с самого начала?

Для первой production-версии модульный монолит предпочтительнее:

- единые модели предметной области и транзакции;
- меньше сетевых вызовов между внутренними сервисами;
- проще отладка, деплой и тестирование;
- API и фоновые задачи можно масштабировать независимо;
- при росте нагрузки отдельные модули можно вынести в самостоятельные сервисы.

Главное архитектурное правило: обработчики HTTP не обращаются напрямую к Blizzard или Warcraft Logs. Они работают через прикладные сервисы, которые используют кеш, хранилище и очередь обновления.

Так мы избегаем ситуации, когда каждый посетитель сайта создаёт множество внешних API-запросов.

## 4. Функциональные модули

### 4.1. Character Service — профиль персонажа

Входные параметры: регион, игровой сервер, имя персонажа.

Последовательность обработки:

1. Проверить формат региона, сервера и имени.
2. Разрешить игровой сервер в канонический идентификатор Blizzard.
3. Найти актуальный профиль в кеше или PostgreSQL.
4. При отсутствии данных поставить задание на загрузку.
5. Получить профиль, специализацию, характеристики и экипировку.
6. Нормализовать данные, проверить полноту и сохранить.
7. Передать их модулям анализа.

Внутренние идентификаторы будут отделены от игровых имён. Это важно при переименовании персонажей и переносах между серверами.

На одном подходящем предмете отсутствует зачарование. Рекомендуется проверить его применимость.

Все значения вымышленные и демонстрируют только формат интерфейса.

Анализ включает:

- экипированные предметы и средний item level;
- наличие допустимых зачарований и камней;
- бонусы комплектов;
- характеристики Haste, Critical Strike, Mastery и Versatility;
- совместимость экипировки со специализацией;
- сравнение с подходящей эталонной выборкой.

Система не будет объявлять предмет «BiS» только потому, что у него выше item level. Для достоверных советов потребуются актуальные правила специализации и, в дальнейшем, интеграция с результатами симуляций.

### 4.3. Talent Analyzer — таланты

Для каждого класса и специализации будет использоваться отдельный набор правил, учитывающий игровой патч, сезон и тип контента.

Предусмотрены три контекста: рейды, Mythic+ и универсальный PvE.

Система сравнивает выбранные таланты с проверенным эталонным билдом, находит отличающиеся узлы и объясняет возможные компромиссы. Если актуального эталона нет, показывает билд без оценки вместо сомнительной рекомендации.

Правила будут версионироваться. После выхода патча прежняя оценка автоматически не переносится на новую версию игры.

### 4.4. Combat Analyzer — DPS, HPS и ротация

Это наиболее технически сложный модуль.

Источником служат доступные публичные отчёты Warcraft Logs. В его GraphQL-схеме предусмотрены события урона, лечения, применений способностей, прерываний, смертей и эффектов.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://www.warcraftlogs.com\&sz=32)

warcraftlogs.com+1



| Показатель     | Способ анализа                              |
| -------------- | ------------------------------------------- |
| DPS            | Урон за выбранное время боя                 |
| HPS            | Эффективное лечение за выбранное время      |
| Overhealing    | Избыточное лечение относительно общего      |
| Cooldown usage | Частота применения доступных способностей   |
| Buff uptime    | Доля времени действия эффекта               |
| Death timeline | Время смерти и предшествующие события       |
| Interrupts     | Выполненные прерывания                      |
| Rotation       | Порядок и интервалы применения способностей |

У DPS и HPS обязательно фиксируются методика расчёта, период боя, источник и включённые типы урона или лечения. Это позволит отличать собственные вычисления от показателей Warcraft Logs.

Анализ ротации будет построен по событиям: последовательность способностей, интервалы, использование ресурсов и ключевых эффектов — насколько эти данные содержатся в логе.

Нельзя автоматически считать каждую смерть ошибкой игрока, а каждый пропущенный cooldown — потерей урона. Поэтому рекомендации должны содержать доказательство и уровень уверенности.

### 4.5. Mythic+ и Raid Progress

Для Mythic+ сохраняем доступные результаты прохождений, уровень ключей, время, рейтинг и сезон. Для рейдов — босса, сложность, наличие убийства и доступные результаты боёв.

Сезоны, подземелья, идентификаторы боссов и уровни прогресса подгружаются из каталогов данных, а не фиксируются навсегда в коде.

### 4.6. Guild Analyzer

Модуль получает состав гильдии через Blizzard API и формирует сводную статистику.

Функции:

- распределение участников по классам, специализациям и ролям;
- средний и медианный item level для доступных профилей;
- сводка экипировки, зачарований и комплектов;
- рейдовый и Mythic+ прогресс;
- поиск потенциальных проблем с экипировкой;
- сравнение участников внутри одной специализации;
- статистика участия в боях, когда доступны публичные логи.

Обязательно показываем охват данных. Например, если удалось обновить только 600 из 900 персонажей, выводим «600 из 900 проверено», а не выдаём результаты за анализ всей гильдии.

### 4.7. Character Comparison

В первой версии сравниваем до пяти персонажей одновременно.

Сопоставлять будем экипировку, характеристики, таланты, Mythic+ и рейдовые достижения. Боевые показатели сравниваются корректно только внутри подходящей выборки: одинаковый босс, сложность, игровой патч, роль и сопоставимые условия.

## 5. Правила аналитической оценки

Создадим Rule Engine — независимый механизм, который исполняет версионированные правила и возвращает структурированные рекомендации.

Каждое правило должно иметь идентификатор, версию, применимость, условия, серьёзность замечания и ссылку на обоснование.

Пример классификации:

| Результат      | Значение                                       |
| -------------- | ---------------------------------------------- |
| &#x20;OK       | Проверка успешно пройдена                      |
| &#x20;Info     | Информационное наблюдение                      |
| &#x20;Warning  | Потенциальная проблема                         |
| &#x20;Critical | Существенное нарушение подтверждённого правила |
| &#x20;Unknown  | Недостаточно данных для вывода                 |

Примеры правил:

- `GEAR_MISSING_ENCHANT` — отсутствует применимое зачарование.
- `GEAR_SET_BONUS` — проверка активированных бонусов комплекта.
- `TALENT_BUILD_DIFF` — расхождение с актуальным эталоном.
- `COMBAT_COOLDOWN_USAGE` — анализ применения важных способностей.
- `COMBAT_BUFF_UPTIME` — анализ времени действия эффектов.
- `PROGRESS_SEASON_MISMATCH` — данные относятся к другому сезону.

Предлагаю не рассчитывать единый универсальный балл «качества игрока» от 0 до 100 на первом этапе. Такой показатель смешал бы несопоставимые роли, типы контента и полноту логов.

Вместо него будем выводить отдельные оценки состояния экипировки, достоверности данных, боевой статистики и прогресса, причём каждый результат будет сопровождаться объяснением.

## 6. Структура базы данных PostgreSQL

Все игровые сущности связываются через внутренние идентификаторы. Данные источников сначала нормализуются, затем сохраняются.

| --------------------- | ----------------------------------------- |
| `characters`          | Регион, сервер, имя, класс, специализация |

| `equipment_items`     | Экипировка персонажа по слотам            |
| `item_catalog`        | Справочник игровых предметов              |
| `talent_loadouts`     | Наборы выбранных талантов                 |
| `guilds`              | Гильдии и серверы                         |
| `guild_memberships`   | Состав и подтверждённое членство          |
| `seasons`             | Сезоны WoW Retail                         |
| `dungeons`            | Подземелья и идентификаторы               |
| `mythic_runs`         | Результаты Mythic+                        |
| `raid_encounters`     | Боссы и сложности                         |
| `raid_progress`       | Прогресс персонажей и гильдий             |

Для персонажей используем составной ключ поиска `region + realm + name`, а внутренние идентификаторы отделяем от идентификаторов Blizzard. Перенос персонажа на другой сервер не должен автоматически объединять две записи: Blizzard указывала, что ID персонажа не гарантированно сохраняется после переноса.&#x20;

### Индексы

Приоритетные индексы: персонаж по региону, серверу и нормализованному имени; участники по гильдии; Mythic+ по персонажу и сезону; боевые метрики по отчёту, бою и персонажу; результаты анализа по версии правил.

Для таблиц боевой статистики предусмотрим партиционирование по времени при достижении значительного объёма данных. На старте обычных индексов PostgreSQL достаточно.

### Срок хранения и удаление

Это важно для публичного проекта. В опубликованном разъяснении Blizzard требуется перепроверять персональные данные персонажей не реже чем раз в 30 дней и удалять данные, которые перестали быть доступными, в частности при подтверждённом ответе 404. Действующую редакцию условий нужно дополнительно проверить перед публикацией сервиса.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://us.forums.blizzard.com\&sz=32)

Blizzard Forums



Поэтому проектируем:

- автоматическую повторную проверку профилей до истечения 30 дней;
- удаление устаревших идентифицируемых снимков;
- каскадную очистку кеша и связанных результатов;
- прекращение отображения данных, которые больше нельзя публиковать;
- отдельные правила хранения исторической статистики с учётом разрешений источника.

Бессрочное хранение истории персонажей в основной архитектуре не предусматриваем. Это предотвращает нарушение требований к сроку жизни данных.

## 8. Как будет работать обновление персонажей

Данные актуальны

Данные устарели или отсутствуют

### Кеширование

Предлагаемые начальные TTL для внутренних кешей:

| Данные                          | TTL                                      |
| ------------------------------- | ---------------------------------------- |
| Профиль персонажа               | 15 минут                                 |
| Экипировка                      | 15 минут                                 |
| Таланты                         | 30 минут                                 |
| Mythic+                         | 15 минут                                 |
| Состав гильдии                  | 60 минут                                 |
| Статические игровые справочники | До изменения версии                      |
| Результаты анализа              | До обновления исходных данных или правил |

Это параметры проекта, а не гарантированные интервалы обновления Blizzard.

При устаревших данных применяем `stale-while-revalidate`: возвращаем допустимые ранее полученные данные, явно сообщаем об их возрасте и запускаем обновление.

Если персонаж более недоступен по правилам источника, его старый профиль показывать нельзя.

### Защита от перегрузки внешних API

Все обработчики используют:

- централизованный лимитер запросов по каждому источнику;
- объединение одинаковых одновременных запросов;
- ограничение количества активных Go workers;
- очереди с приоритетами;
- повторные запросы с экспоненциальной задержкой и случайным разбросом;
- `Retry-After` от провайдера;
- circuit breaker при массовых ошибках.

Warcraft Logs учитывает потребление API в баллах за час, поэтому будем отслеживать фактические доступные баллы, а не только количество HTTP-запросов.&#x20;

Для первой версии рекомендую долговременную очередь заданий в PostgreSQL с контролируемым захватом задач и Redis для кеша, распределённых ограничителей и подавления дубликатов. При росте нагрузки очередь можно вынести в NATS JetStream или RabbitMQ.

## 9. Безопасность

Публичный доступ без обязательной регистрации означает, что нам особенно важно защищать ресурсы сервера и внешние API.

| Риск                                    | Решение                                        |
| --------------------------------------- | ---------------------------------------------- |
| Утечка Blizzard Client Secret           | Только серверное хранение секретов             |
| Злоупотребление поиском                 | Rate limiting и защита от ботов                |
| SQL Injection                           | Параметризованные SQL-запросы                  |
| XSS                                     | Экранирование данных, CSP                      |
| SSRF                                    | Запрет произвольных внешних URL                |
| DDoS                                    | CDN/WAF и ограничения запросов                 |
| Компрометация административного доступа | OIDC, MFA, RBAC                                |
| Утечка данных игроков                   | Минимизация, удаление, контроль срока хранения |
| Перегрузка внешних API                  | Бюджеты, очереди, circuit breaker              |
| Утечка подробностей ошибок              | Безопасные публичные сообщения                 |

Отдельные требования:

Авторизация. Для публичного просмотра учётная запись не нужна. OAuth Client Credentials используется между нашим сервером и поставщиками API. Административная панель будет защищена отдельно.

Валидация. Все входные параметры имеют ограничения длины, допустимые значения и проверяемые форматы. URL внешних API формируются только приложением из разрешённых доменов. Произвольные GraphQL-запросы пользователи отправлять не смогут.

Логирование. Не сохраняем токены, секреты, заголовки авторизации и другие чувствительные значения. Каждому запросу назначаем `request_id`.

Защита данных. Предусмотрим политику конфиденциальности, механизм обращения по поводу данных персонажа и автоматическое удаление информации, доступ к которой был отозван.

## 10. Обработка ошибок

Ошибки будем классифицировать на ошибки пользователя, внешнего источника, бизнес-правил и внутренней инфраструктуры.

| HTTP | Ситуация                          | Поведение                                  |
| ---- | --------------------------------- | ------------------------------------------ |
| 400  | Неверные параметры                | Объяснить, какое поле ошибочно             |
| 404  | Персонаж не найден или недоступен | Не показывать недействительные данные      |
| 409  | Конфликт операции                 | Вернуть описание конфликта                 |
| 422  | Невозможная комбинация параметров | Показать причину                           |
| 429  | Превышен лимит пользователя       | Сообщить период повтора                    |
| 502  | Некорректный ответ поставщика     | Зарегистрировать ошибку                    |
| 503  | Внешний сервис недоступен         | Допустимый кеш или временная недоступность |
| 504  | Тайм-аут                          | Завершить запрос с понятной ошибкой        |

Для долгого анализа возвращается `202 Accepted` с ID задания. Пользователь сможет увидеть состояние обработки: `queued`, `running`, `completed` или `failed`.

Внутренние ошибки должны быть типизированными, чтобы бизнес-логика не зависела от HTTP-кодов.

Для фоновых заданий предусмотрены идемпотентность, ограниченные повторы и отдельное состояние окончательного отказа. Неуспешные задачи не должны бесконечно загружать Blizzard API.

## 12. Масштабирование и производительность

Сразу заложим горизонтальное масштабирование Go API и workers.

Предварительные целевые показатели, подлежащие нагрузочному тестированию

Кешированный GET, p95

# ≤ 250 мс

Доступность

# 99,9%

Пиковая нагрузка API

# 1 000 RPS

Преимущественно кешированные запросы

Начальная ёмкость

# 100 тыс.

Отслеживаемых персонажей

Эти цифры — цели проектирования, а не обещанная производительность. Конкретные возможности зависят от оборудования, нагрузки, объёма данных и ограничений внешних API.

Важнее всего разделить:

- HTTP-нагрузку, которую можно масштабировать за счёт реплик и кеша;
- скорость получения новых данных, ограниченную провайдерами;
- тяжёлый анализ боевых логов, выполняемый отдельными workers.

Для мониторинга используем Prometheus, Grafana, OpenTelemetry и централизованное логирование.

Ключевые метрики: p95/p99 задержки, cache hit ratio, ошибки провайдеров, глубина очередей, возраст данных, стоимость запросов Warcraft Logs, количество проверенных персонажей и время расчёта анализов.

## 13. Стратегия тестирования

Предлагаю следующую матрицу:

| Тип тестирования | Что проверяем                            | Инструменты                          |
| ---------------- | ---------------------------------------- | ------------------------------------ |
| Unit             | Правила анализа, расчёты, валидация      | Go `testing`                         |
| HTTP             | Обработчики, DTO, middleware             | `httptest`                           |
| Integration      | PostgreSQL, Redis, миграции              | Testcontainers                       |
| Contract         | Форматы Blizzard и Warcraft Logs         | Зафиксированные API fixtures         |
| E2E              | Поиск, профиль, сравнение, гильдия       | Playwright                           |
| Load             | Пропускная способность, p95/p99          | k6                                   |
| Race             | Конкурентный доступ и горутины           | Go Race Detector                     |
| Security         | Некорректные данные, ограничения, доступ | OWASP ZAP и специализированные тесты |

### Обязательные тестовые сценарии

1. Персонаж найден, профиль корректен и актуален.
2. Персонаж отсутствует или стал недоступен.
3. Игровой сервер либо имя указаны некорректно.
4. Специализация поменялась после обновления.
5. Отсутствует экипировка или часть характеристик.
6. Доступны таланты, но отсутствует актуальный набор правил.
7. Для персонажа нет публичных боевых логов.
8. Лог содержит неполный бой или пропущенные события.
9. Blizzard или Warcraft Logs возвращает 429.
10. Несколько пользователей одновременно ищут одного персонажа.
11. Состав гильдии изменился во время обновления.
12. Произошёл переход на новый игровой сезон.
13. Данные персонажа необходимо удалить.
14. Worker завершился аварийно и повторно получил задание.
15. Два персонажа имеют одинаковые имена на разных серверах.

Для правил анализа целевой уровень покрытия ветвей — не менее 90%. При этом не будем ориентироваться только на процент покрытия: нужны эталонные наборы входных данных с заранее проверенными результатами для разных классов, ролей и условий боёв.

В CI/CD включим линтеры, тесты, проверку миграций, сканирование зависимостей и сборку Docker-образов. Деплой в production происходит только после прохождения проверок.

## 16. Архитектурное решение для утверждения

Рекомендую принять эту архитектуру как базовую v1.0 с тремя принципиальными условиями:

1. Blizzard остаётся основным поставщиком игровых данных; Warcraft Logs подключается для анализа публичных боёв, а Raider.IO — только после решения вопроса об условиях использования.
2. Анализатор выдаёт объяснимые рекомендации по актуальным правилам и не маскирует отсутствие достоверных данных оценками.
3. Go API, Go workers и React разворачиваются независимо, но на первом этапе используют общую модульную архитектуру и PostgreSQL.

Перед реализацией понадобится дополнительно зафиксировать только эксплуатационные параметры: серверный бюджет, список запускаемых регионов, допустимую частоту обновления и источники эталонных билдов. Они не мешают утвердить предложенную базовую архитектуру.

Код пока не пишем. Следующий шаг после утверждения — спецификация MVP: модели, SQL-схема, OpenAPI-контракты, интерфейсы адаптеров, первые правила анализа и тест-кейсы, после чего можно переходить к реализации.
