# Первые правила анализа — спецификация

Версия: 0.1 · 30 октября 2026. Основание: утверждённая архитектура v1.0.

Этот документ задаёт поведение механизма правил, реализованного во втором этапе. В MVP первого этапа доступны профиль, экипировка, характеристики, таланты и сведения о полноте данных. Текущий механизм проверен синтетическим набором; действующие игровые правила и эталонные билды пока не подключены. [Результаты реализации](../operations/analysis-validation.md), [каталог и его ограничения](../../rules/README.md).

## Границы выводов

- Отсутствие данных не является ошибкой игрока. Неизвестное значение не заменяется нулём, пустым списком или утверждением об отсутствии эффекта.
- Более высокий уровень предмета сам по себе не доказывает преимущество предмета. Правила ниже не определяют BiS, ожидаемый прирост DPS/HPS или качество игрока.
- Нет универсального балла 0–100. Полнота данных, факты об экипировке и рекомендации показываются отдельно.
- Изображённые таланты не получают оценку без подтверждённого эталона для того же контекста. Расхождение с эталоном само по себе не означает ошибку.
- Правила работают с нормализованным неизменяемым снимком. Они не обращаются к внешним API и не изменяют исходные данные.

## Контракт правила и результата

До активации правило должно иметь следующие поля:

| Поле | Смысл |
| --- | --- |
| `rule_id`, `rule_version` | Стабильный код правила и версия алгоритма |
| `ruleset_version`, `ruleset_digest` | Версия и контрольная сумма проверенного набора правил |
| `game_flavor` | Только `retail` для этого проекта |
| `patch`, `season`, `class_id`, `specialization_id`, `content` | Область применимости; `content`: raid, mythic_plus или general_pve |
| `required_sections` | Обязательные секции и необходимые поля |
| `references`, `reviewed_at`, `reviewed_by` | Источник обоснования, дата и ответственный за проверку |
| `enabled` | Включение только после проверки источника и тестов |

Контекст должен задаваться явно. Отсутствие патча или специализации в снимке не означает разрешение выбрать «последний» набор правил. `season` может быть неприменим для конкретного правила, но это должно быть явно зафиксировано в его области применимости. Неизвестный контекст приводит к `unknown`, если он необходим правилу.

Результат содержит `snapshot_id`, `rule_id`, обе версии, digest, контекст, `evaluated_at`, `applicability`, `outcome`, `confidence`, `reason_code`, `message_key`, параметры локализации и доказательства. Доказательство ссылается на конкретные нормализованные поля снимка, их `fetched_at`, источник и проверенный пункт набора правил. URL источника хранится как ссылка, а не как автоматически исполняемое содержимое.

`applicability` и `outcome` описывают разные свойства:

| Применимость | Результат | Поведение |
| --- | --- | --- |
| `applicable` | `OK`, `Info`, `Warning`, `Critical` или `Unknown` | Правило относится к контексту; `Unknown` означает недостаток данных для проверки |
| `not_applicable` | `null` | Правило заведомо не относится к контексту; рекомендация не создаётся |
| `unknown` | `Unknown` | Нельзя установить применимость: например, неизвестны патч или свойства предмета |

`OK` — подтверждённое выполнение проверки; `Info` — факт или допустимое расхождение; `Warning` — подтверждённая потенциальная проблема; `Critical` — только нарушение отдельно подтверждённого существенного ограничения. Ни одно из первых трёх игровых правил не выдаёт `Critical` по умолчанию.

Для первых правил `confidence` принимает `high`, `medium` или `unknown` и имеет текстовое обоснование. Это качественная оценка доказательств, а не вымышленная вероятность. Для `Unknown` используется `unknown`; числовой эффект на эффективность не оценивается.

Повторное исполнение над одинаковыми снимком, контекстом и набором правил даёт одинаковый содержательный результат. Локализация меняет только сообщения, но не исход, применимость или доказательства. Ключ кеша анализа включает снимок, версии и digest правил, контекст и язык представления.

## Достоверность и полнота данных в MVP

Это диагностические состояния данных первого этапа, а не игровые рекомендации:

| Код | Условие | Отображение |
| --- | --- | --- |
| `DATA_SECTION_PARTIAL` | Секция получена, но часть ожидаемых полей не подтверждена | «Данные неполные»; перечислить неизвестные поля без отрицательной оценки игрока |
| `DATA_SECTION_UNAVAILABLE` | Секция не получена, временно недоступна либо источник её не предоставляет | «Нет данных» с безопасной причиной; пустой набор не подставляется |
| `DATA_STALE` | Данные прошли `fresh_until`, но ещё допустимы к показу | Возраст данных и состояние фонового обновления |
| `DATA_CONTEXT_UNKNOWN` | Не подтверждены необходимые патч, сезон или специализация | Показать факты; оценка зависимых правил недоступна |
| `DATA_RULESET_UNAVAILABLE` | Нет проверенного набора для контекста | «Оценка недоступна: нет проверенного набора правил» |

Полнота (`complete`, `partial`, `unavailable`) независима от свежести (`fresh`, `stale`, `pending`, `unavailable` в метаданных ответа). Полностью полученная секция может устареть; свежая секция может содержать неполные данные. `complete` означает полноту нормализации доступного ответа провайдера, а не гарантированное знание всех механик игры.

Истечение `valid_until`, подтверждённая недоступность профиля и quarantine имеют приоритет над диагностикой: скрытые данные не передаются механизму правил и не возвращаются из кеша анализа. Срок конкретной секции не продлевается только потому, что профиль был проверен повторно.

В исходном MVP первого этапа `/analysis` не публиковался. Контракт v0.2 добавляет этот маршрут и отдельную вкладку; `meta.coverage` по-прежнему описывает четыре исходные секции. Результат `Unknown` не подменяет HTTP-ошибку и не открывает скрытые данные.

## `GEAR_MISSING_ENCHANT`

Назначение: найти подтверждённое отсутствие применимого постоянного зачарования на конкретном экипированном предмете.

Для проверки нужны слот, предмет и его свойства, достоверность списка зачарований, специализация/роль при необходимости и проверенная матрица применимости для заданного патча. Пустой список зачарований допустимо интерпретировать как отсутствие только если адаптер явно подтвердил полноту этого поля. Отсутствующее поле API не равно пустому списку.

| Условия | Применимость и исход |
| --- | --- |
| Матрица подтверждает, что предмет не подлежит проверяемому зачарованию | `not_applicable`, `null` |
| Применимость или полнота поля неизвестны | `unknown`/`applicable`, `Unknown`, причина `ENCHANT_APPLICABILITY_UNKNOWN` или `ENCHANT_DATA_INCOMPLETE` |
| Применимость подтверждена, совместимое зачарование присутствует | `applicable`, `OK` |
| Применимость подтверждена, полный список не содержит совместимого зачарования | `applicable`, `Warning` |

Доказательство предупреждения: слот, идентификатор предмета из снимка, подтверждённое отсутствие применимого зачарования, ссылка на матрицу и её версию. Сообщение предлагает проверить/добавить применимое зачарование. Утверждения о потере урона и конкретной цене отсутствуют. Особые случаи, исключения и временные эффекты должны быть описаны матрицей, иначе результат `Unknown`.

## `GEAR_SET_BONUS`

Назначение: показать подтверждённый состав комплекта и активированные бонусы. Проверка не требует надеть максимальное число частей комплекта для каждого персонажа.

Нужны идентификаторы комплекта и предметов, информация об экипированных частях, порогах бонусов и совместимости с контекстом. Если источник явно сообщает активные бонусы, MVP может показать этот факт с происхождением данных; вывод о корректности сборки всё равно требует проверенного правила.

| Условия | Применимость и исход |
| --- | --- |
| Проверенная область правила исключает контекст/тип предметов | `not_applicable`, `null` |
| Неизвестны состав комплекта, пороги, контекст или полнота экипировки | `unknown`/`applicable`, `Unknown` |
| Подтверждены число частей и активные бонусы без отдельной цели сборки | `applicable`, `Info` |
| Проверенная цель для данного контекста выполнена | `applicable`, `OK` |
| Проверенная явная цель для данного контекста не выполнена | `applicable`, `Warning` с описанием цели и ограничений |

Число частей не заменяет сведения об активации бонуса при наличии неоднозначных игровых условий. Различные комплекты не складываются. Бонус не считается неактивным только из-за отсутствующего поля. Правило не советует заменить предмет без оценки применимых ограничений.

## `TALENT_BUILD_DIFF`

Назначение: объяснить отличия активного набора талантов от проверенного эталона того же класса, специализации, версии дерева, патча и типа контента.

Эталон хранит provenance, узлы, выбранные варианты, ранги и допустимые альтернативы. Совпадение строк экспорта не является единственным критерием. Если невозможно надёжно декодировать дерево или определить активный набор, результат `Unknown`.

| Условия | Применимость и исход |
| --- | --- |
| Нет эталона для требуемого контекста либо не подтверждены патч/версия дерева | `unknown`, `Unknown`, причина `TALENT_BASELINE_UNAVAILABLE` или `TALENT_CONTEXT_UNKNOWN` |
| Выбор узлов неполон/несовместим с доступным каталогом | `applicable`, `Unknown`, причина `TALENT_DATA_INCOMPLETE` |
| Выбор совпадает с эталоном с учётом допустимых альтернатив | `applicable`, `OK` |
| Есть отличия, но отсутствует доказательство нарушения ограничения | `applicable`, `Info` со списком узлов/рангов и возможными компромиссами |
| Нарушено отдельно подтверждённое ограничение выбранного контекста | `applicable`, `Warning` со ссылкой на это ограничение |

Выбор другого utility-таланта не получает `Warning` автоматически. Смена специализации делает предыдущий результат неприменимым к новому снимку. При смене патча старый эталон не наследуется без новой проверки. Отсутствие эталона не мешает показать полученные таланты.

## Наборы данных для проверки

Все перечисленные ниже наборы **синтетические**: они задают ветви алгоритма, не являются реальными ответами Blizzard и не подтверждают текущие правила Retail.

| Набор | Минимальное условие | Ожидаемый результат |
| --- | --- | --- |
| `SYN_ENCHANT_PRESENT` | Применимость подтверждена, совместимое зачарование присутствует | `OK` |
| `SYN_ENCHANT_ABSENT` | Применимость подтверждена, полный список пуст | `Warning` |
| `SYN_ENCHANT_OMITTED` | Поле зачарований не получено | `Unknown` |
| `SYN_ENCHANT_INAPPLICABLE` | Матрица исключает предмет | `not_applicable` |
| `SYN_SET_KNOWN` | Известны части и бонусы, цели нет | `Info` |
| `SYN_SET_PARTIAL` | Не подтверждён один из необходимых слотов | `Unknown` |
| `SYN_TALENT_MATCH` | Полный набор совпал с допустимым эталоном | `OK` |
| `SYN_TALENT_DIFFERENT` | Различие разрешено, нарушение не доказано | `Info` |
| `SYN_TALENT_NO_BASELINE` | Эталон отсутствует | `Unknown` |
| `SYN_PATCH_UNKNOWN` | Не подтверждён обязательный патч | `Unknown` |

Для этапа 2 каждый включаемый набор должен пройти ветви применимости, неполноты, исключений и смены контекста. Цель покрытия ветвей механизма правил — не менее 90%, дополнительно требуются проверенные ожидаемые результаты. Достижение процента без проверки этих сценариев не является основанием активации.

Действующие внешние fixtures появятся при реализации адаптера: с датой получения, endpoint, регионом, обезличиванием и проверкой допустимости хранения. Синтетические примеры хранятся отдельно и явно помечаются. Публичный запуск рекомендаций требует выбранного источника эталонов и завершённой проверки его условий использования.
