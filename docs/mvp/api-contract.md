# REST API v0.9

Эксплуатационное дополнение 0.6.0: `/api/v1/runtime` подчиняется общему read limiter и может вернуть 429 с `Retry-After`. Внутренний `/metrics` возвращает Prometheus text, а при ошибке БД/ledger — 503 с `kipet_metrics_scrape_success=0`. API и worker имеют отдельные внутренние listeners; публичный nginx закрывает `/health/*` и `/metrics`. Gateway сохраняет JSON-ошибку 413 для больших тел; social API ограничен 8192 байтами, refresh персонажа — 4096. Подробнее — [эксплуатационные проверки](../operations/release-validation.md).

Дата: 1 ноября 2026. Контракт локальной реализации этапов 1–5 утверждённой архитектуры v1.0. Машиночитаемый источник: [mvp-v1.yaml](../../api/openapi/mvp-v1.yaml). Значения в примерах синтетические и не являются ответами Blizzard или Warcraft Logs.

## Границы

Публичный API обслуживает EU/US без регистрации. Экипировка, характеристики, таланты, Mythic+ и рейдовый прогресс отображаются как наблюдения источника. Объяснимый анализ использует только набор правил точного контекста с подтверждённой provenance; при его отсутствии возвращается Unknown. Реальный каталог пока пуст, синтетический доступен только для fixture. Публичные боевые отчёты обрабатываются отдельной подсистемой.

## Идентичность и входные данные

Ключ поиска: `region + canonical realm ID + NFC(casefold(NFC(name)))`. `region` равен `eu` или `us`. Внутренний UUID персонажа отличается от Blizzard ID; одинаковые имена на разных серверах — разные записи. Перенос и переименование автоматически не объединяют записи по совпадению ID.

`realm` в API — точный канонический slug из локального каталога Blizzard, включая Unicode, если он присутствует в каталоге. Пользователь вводит локализованное имя сервера в UI, выбирает результат `/meta/realms`, после чего UI отправляет canonical slug. Запрещено самостоятельно транслитерировать имя, подставлять slug другого провайдера или произвольный URL. Неизвестный slug — `404 REALM_NOT_FOUND` после успешной проверки каталога; при недоступном/неинициализированном каталоге — `503`, без отрицательного кеширования.

Имя проходит однократное URI decoding, trim, NFC, Unicode case folding и повторный NFC для ключа. Принимаются Unicode letters и combining marks, начинающиеся с буквы. Предел проекта — 2–24 Unicode code points после первого NFC; это предел входного контракта, а не утверждение об игровых правилах именования. Control characters, whitespace внутри имени, path separators и пунктуация запрещены. Нельзя использовать ASCII-only regex. Нормализованный ключ после case folding ограничен 48 code points, поскольку folding может увеличить длину; некорректная percent encoding даёт `400`. Поля JSON, не описанные в схеме, отклоняются. Для POST: `application/json`, максимум 4 KiB.

`locale=ru-RU|en-US` — язык представления, по умолчанию `ru-RU`; он не создаёт новую идентичность и не входит в dedup key загрузки. Отсутствующий перевод показывается разрешённым fallback из нормализованного каталога. Если перевод невозможно сформировать, nullable label остаётся `null`; ID сохраняется. Локализованные ключи Redis разделяются, а идентичность и фоновые задания остаются общими.

`/meta/realms`: `region` обязателен, `q` — префикс локализованного имени или slug после той же Unicode нормализации, `limit` от 1 до 100 (по умолчанию 30). Порядок — slug, затем realm ID. Непрозрачный cursor связан с `region`, `locale`, `q` и версией каталога; несовпавший, устаревший или повреждённый cursor даёт `400 INVALID_ARGUMENT`, UI начинает поиск заново. Пустой результат поиска — `200 items:[]`, не `404`. Каталог загружается фоновым процессом, HTTP handler не запрашивает Blizzard.

## Ответы и полнота

Успешный ответ содержит `{data, meta, request_id}`. Ошибка содержит `{error, request_id}`. `request_id` — серверный UUID, совпадающий с `X-Request-ID`. Все даты — UTC RFC 3339. Внешние ID — положительные десятичные строки в пределах int64; исключение — nullable ID loadout, для которого контракт допускает также строку `"0"`, если её явно предоставил источник. Неизвестный ID остаётся `null`. Внутренние ID — UUID. Это сохраняет точность при чтении JavaScript клиентом.

Обязательные поля `meta`:

| Поле | Семантика |
| --- | --- |
| `source` | `blizzard` для реальных игровых данных и ожидаемой загрузки; `fixture` для явно выбранных синтетических примеров; `system` для jobs/health/операционного результата refresh |
| `fetched_at` | Самое раннее фактическое получение возвращаемых секций; не время HTTP-запроса. Для jobs/health и pending — `null` |
| `status` | `fresh`, `stale`, `pending`, `unavailable` |
| `snapshot_id` | UUID опубликованного снимка или `null` для pending/jobs/health/каталога |
| `valid_until` | Самый ранний предел допустимого показа возвращаемых секций; `null`, если данных нет или срок неприменим |
| `patch`, `season` | Подтверждённая версия данных и ID сезона, иначе `null`; номер патча нельзя вывести из текущей даты |
| `locale` | Выбранный язык представления |
| `coverage` | Метаданные отдельных секций; `{}` для jobs/health/pending |
| `job_id` | Текущее активное обновление, иначе `null`; в `202` всегда UUID |

`coverage` использует ключи `profile`, `equipment`, `statistics`, `talents`, `mythic_plus`, `raids`, `realms`. Профиль сообщает шесть секций; анализ использует четыре исходные секции. Секция содержит `state=complete|partial|unavailable`, `fetched_at`, `fresh_until`, `valid_until`, `reason`. Для `complete` причина равна `null`; для `partial`/`unavailable` безопасная причина выбирается из `never_fetched`, `provider_unavailable`, `not_provided`, `invalid_response`, `expired`. Неполученное поле не превращается в ноль, пустой массив или отрицательное заключение.

`fresh` означает, что возвращаемые данные моложе своего TTL, а не что профиль только что обновился в игре. `partial` описывает полноту и может сочетаться с `fresh` либо `stale`. Если ответ содержит несколько секций, `status=stale`, когда хотя бы одна возвращённая секция вышла за свой TTL. Времена отсутствующих секций равны `null`; данные за пределом `valid_until` не возвращаются. Свежесть профиля не продлевает срок старой экипировки или талантов.

Начальные TTL проекта: профиль, экипировка, характеристики, Mythic+ и рейды — 15 минут; таланты — 30 минут. Существующие допустимые stale данные возвращаются сразу, обновление ставится в очередь. Недоступность очереди при наличии допустимого stale ответа не прячет данные: `200 stale`, `job_id:null`; метрика фиксирует невозможность обновления. Время провайдерского обновления не обещается.

Для unavailable-секции автоматический GET-refresh разрешён не раньше её последнего `checked_at + TTL`, кроме `never_fetched`: первая загрузка ставится сразу. Отсутствие payload не означает разрешение нового сбора при каждом чтении; `checked_at` хранится внутри приложения и не подменяет публичный `fetched_at`. Пользовательский POST подчиняется собственным лимитам и cooldown.

## Статусы и жизненный цикл

| Состояние | HTTP и поведение |
| --- | --- |
| Пригодный профиль, нужная секция свежая | `200`, `meta.status=fresh` |
| Пригодные stale данные, срок публикации не истёк | `200 stale`; `job_id` активного задания, если enqueue успешен |
| Пригодный профиль, optional секция не получена | `200 data:null`, `status=unavailable`, coverage секции `unavailable`; обновление может иметь `job_id` |
| Профиля ещё нет либо он больше не пригоден, задание принято | `202 data:null`, `status=pending`, `Location`, `Retry-After`, обязательный `job_id` |
| Корректно подтверждённый summary `404` | `404 CHARACTER_UNAVAILABLE`; старые данные скрыты и поставлены на каскадное удаление |
| Неоднозначный summary `403` | Профиль quarantined; `502 PROVIDER_ACCESS_DENIED`; старые данные скрыты, но один такой ответ не является доказательством для удаления |
| Повторный provider `401` после одного обновления OAuth-токена | `502 PROVIDER_AUTH_FAILURE` без пригодных данных; без purge и бесконечного цикла токенов |
| `404` только необязательной секции | Весь профиль не удаляется; секция unavailable/partial согласно нормализованному ответу |
| Terminal ошибка загрузки без пригодных данных | `502 PROVIDER_INVALID_RESPONSE` либо `503 PROVIDER_UNAVAILABLE`, `error.job_id` завершившегося задания |
| Нет PostgreSQL/очередь заполнена, данных нет | `503 INFRASTRUCTURE_UNAVAILABLE|QUEUE_FULL`; задание не обещается |
| Лимит клиента либо cooldown refresh | `429`, безопасный code и `Retry-After` |

Прежде чем вернуть данные из Redis, application service проверяет в PostgreSQL публикационный статус и сроки персонажа. Quarantine/удаление перекрывают stale cache, включая гонку с worker. HTTP-кеш для идентифицируемых ответов запрещён: `Cache-Control: no-store` для browser/CDN; Redis является внутренним кешем. Иначе уже закешированный профиль мог бы остаться доступным после отзыва.

Провайдерский `429` обрабатывает worker через `retry_wait` и его `Retry-After`; он не превращается в пользовательский `429`. Временный provider timeout не означает, что персонажа нет. Задание не создаётся заново бесконечно после terminal failure: до истечения настроенного cooldown запрос возвращает допустимые старые данные либо terminal `502/503`. По истечении cooldown новое обновление снова допускается по общим лимитам.

Ошибки не содержат тело ответа Blizzard, внутренние SQL, stack trace, worker lease, токены или имена хостов. `error.code` предназначен для клиента, `message` — безопасное отображаемое сообщение, `fields` — только имена полей и причина без отражения ввода. `retry_after_seconds` дублирует минимум задержки из заголовка, если применим; `error.job_id` указывает на относящееся к ошибке завершённое задание, иначе `null`. `retryable` означает допустимость повторного действия при соблюдении cooldown, а не бесконечный автоповтор.

## Refresh и polling

POST принимает только `{region, realm, name, locale?}`. Все шесть секций обновляются общим заданием; публичного `force` нет. Если все секции уже свежие и нет активного задания, возвращается `200` с `data:{disposition:"already_fresh",job_id:null}`, `meta.source=system`, `meta.status=fresh`, `meta.fetched_at=null`, `meta.coverage={}`. Если задание уже активно либо принято новое, возвращается `202` с тем же envelope pending; `Location=/api/v1/jobs/{id}`. Подтверждённый negative-cache профиля может дать `404` до истечения его cooldown. Превышение лимита — `429`, а не неявный обход через GET.

Начальные защитные настройки проекта: чтение 120 запросов/мин/IP с burst 20; refresh 3/мин/IP с burst 1; cooldown персонажа 60 секунд. Это настраиваемые параметры, не SLA. Reverse proxy передаёт IP только через доверенный ingress; произвольный `X-Forwarded-For` не принимается как идентичность клиента. Существует также глобальный бюджет provider calls и ограничение длины очереди. Недоступный Redis не отключает ограничения: используется консервативный PostgreSQL fallback либо возвращается `503`.

GET профиля при отсутствии данных также ограничен публичным read limit, dedup/cooldown, глобальным бюджетом и длиной очереди; он не позволяет бесплатно создать неограниченное число заданий. Повторы одинакового ключа объединяются в PostgreSQL независимо от регистра имени и locale. `202` означает commit задания, а не гарантию успешной загрузки.

GET `/jobs/{id}` для существующего задания всегда возвращает `200` и `data.status=queued|running|retry_wait|succeeded|failed|cancelled`. Это уточнение исходного общего термина `completed`: успешный terminal state называется `succeeded`. Polling не является обновлением состояния и не вызывает провайдера. Терминальные задания имеют `next_poll_after_seconds:null`; завершение может означать частичный снимок, его coverage клиент узнаёт повторным GET профиля/секций. Снимок публикуется только после обязательного успешного summary.

UI соблюдает `Retry-After`, начинает примерно с 3 секунд, при ожидании увеличивает интервал до 15 секунд с jitter, при terminal state прекращает polling. Через 2 минуты UI прекращает автоматический polling, сохраняет job ID и показывает возможность проверить статус вручную; worker продолжает работу. Клиент останавливает повтор при `failed/cancelled`, `404`, ошибке валидации или rate limit до указанного времени. Успешное задание ведёт к повторному GET исходного ресурса, а не к предположению, что все optional секции доступны.

Если проверенный summary по прежнему ключу даёт новый Blizzard ID, fenced transaction удаляет прежний character со снимками и заданиями, создаёт новый UUID и новое queued задание. Старый payload не публикуется; прежний job может вернуть `404 JOB_NOT_FOUND`. В таком случае UI один раз перечитывает исходный профиль и следует новому `job_id`, если он существует; при подтверждённом `404 CHARACTER_UNAVAILABLE` скрывает данные. Если повторное чтение снова не даёт пригодного профиля или нового задания, автоматическое ожидание останавливается. Цикл переходов между удалёнными jobs недопустим.

ID задания — непредсказуемый UUID, не механизм авторизации: публичный endpoint выдаёт только ограниченные операционные поля без имени персонажа. При удалении персонажа связанные задания удаляются либо обезличиваются; удалённый ID возвращает `404 JOB_NOT_FOUND`. Внутренний attempt count, provider payload, dedup key, fencing token и leased_by не публикуются.

## DTO игровых данных

Профиль содержит ID, имя, регион/сервер, уровень, класс, расу, доступную специализацию, фракцию, средний/equipped item level и время последнего входа, если оно предоставлено. Item level не является оценкой качества предмета. Специализация и необязательные значения nullable.

Экипировка — список полученных предметов по нормализованным слотам. Из отсутствия off-hand нельзя делать вывод об ошибке: двуручное оружие допустимо. Нельзя требовать 16 предметов у любого персонажа. Неизвестный нормализованный slot сохраняется отдельной строкой, а не отбрасывается; строковый slot и предел ресурса 32 предмета допускают расширение каталога и не утверждают количество игровых слотов. `enchantments:null` означает неизвестное поле, `[]` — подтверждённое отсутствие; то же относится к sockets. Для известного сокета `item_id:null` означает пустой сокет. Bonus IDs сохраняются, предметы с одинаковым item ID и разными bonus IDs не приравниваются.

Характеристики хранят rating отдельно от percent. `23.5` — процентные пункты. Melee, ranged и spell critical strike/haste передаются отдельно; API не выбирает один показатель без подтверждённого контекста. Versatility сохраняет отдельно damage/healing bonus и damage taken reduction. Mastery/haste не ограничены 100%. Если провайдер не возвращает значение, оно `null`, а completeness отражает пробел. Эти поля — нормализованный контракт, точный provider-to-domain mapping проверяется контрактными fixtures при реализации.

Таланты содержат доступные loadouts, специализацию, active flag, export code/tree hash (nullable) и выбранные node/entry/spell IDs с rank. `is_active:null` означает неподтверждённую активность; `false` допустим только для подтверждённо неактивного набора. `nodes:null` означает неизвестные узлы, `nodes:[]` — подтверждённо пустой набор. Неполный ответ не превращается в «таланты не выбраны». В MVP отсутствует поле score и нет сравнения с воображаемым эталоном. При изменении формата talent tree адаптер отдаёт `partial/unavailable`, не выдумывает узлы.

## Объяснимый анализ

`GET …/analysis` принимает `content=general_pve|raid|mythic_plus` (по умолчанию `general_pve`) и обычный `locale`. Дополнительная оценка не является исходной секцией: `meta.coverage` сохраняет profile/equipment/statistics/talents. Успешный ответ — 200 с `snapshot_id`, источником, явным контекстом, provenance выбранного ruleset, сводкой, результатами и диагностикой. Отсутствие проверенного набора возвращает `ruleset:null` и `Unknown`, без оценки качества игрока. Нет обязательного профиля — обычный 202 с job ID.

Кеш отчётов не зависит от locale и привязан к snapshot, digest каталога/механизма и content. Время `evaluated_at` у кешированного отчёта сохраняется. При истечении срока данных, смене снимка, карантине и purge старый отчёт недоступен. UI сверяет snapshot/content и не показывает чужой или устаревший отчёт; временное несовпадение требует перечитать профиль. Неизвестный content даёт 400 до постановки работы. Правила не вызывают внешний API и не создают боевые рекомендации без подходящего проверенного контекста.

Набор fixture явно вымышленный и применяется только к синтетическому патчу. В режиме Blizzard пока нет активных проверенных игровых наборов. Порядок добавления описан в [rules/README.md](../../rules/README.md).

## Mythic+ и рейды

`GET …/mythic-plus` возвращает nullable `season`, `rating`, `run_scope`, `best_runs`, `available_seasons`. `season` содержит строковый ID, nullable name и nullable `is_current`; календарь и максимальный ID не определяют текущий сезон. `meta.season` соответствует сезону этой секции, а не глобальному контексту анализа. Без подтверждённой связи текущего индекса с выбранным сезоном его рейтинг не переносится в ответ другого сезона.

`run_scope=season_best|current_period_best|unknown` описывает охват наблюдаемого списка. Прохождение содержит dungeon ID/name, keystone level, nullable duration в миллисекундах, дату, признак своевременности и рейтинг источника. Это не полная история ключей, не содержимое Great Vault и не рейтинг Raider.IO. `available_seasons` отражает индекс персонажа; публичный выбор исторического сезона пока не реализован.

`GET …/raids` возвращает expansions → instances → modes → encounters. Сложность и статус нормализованы из значений источника; неизвестный вариант остаётся `unknown`. Счётчики завершённых/всех боссов и число убийств nullable. Подтверждённый `0` отличается от неизвестного; дата последнего убийства при нуле может отсутствовать. Ответ может включать исторические рейды и не обещает отдельную выборку «текущего» рейда. `meta.season=null`.

Во всех коллекциях прогресса `null` означает отсутствие наблюдения, `[]` — явно полученный пустой список. Некорректные строки не превращаются в игровые нули; сохранившаяся часть получает partial coverage. Новые секции не используются движком правил и не продлевают кеш анализа. Клиент проверяет совпадение character ID и snapshot ID с показанным профилем.

## Боевые отчёты

Ответ анализа участника может содержать `combatant_stats`. Это один снимок выбранного участника в пределах боя. `observed_at_ms` задаёт время от начала отчёта, а `values` содержит доступные значения источника. Нулевые значения сохраняются. Старые снимки и бои без подходящего события возвращаются без этого поля.

Код отчёта — ровно 16 ASCII букв/цифр с сохранением регистра. Fight ID и `actor_id` — положительные int32, единственное значение параметра без знака/ведущих нулей. HTTP не принимает внешний URL или текст GraphQL; UI может извлечь код только из точной HTTPS-ссылки Warcraft Logs. Локаль не меняет расчёт. Источник в `meta.source` — `fixture` либо `warcraftlogs`; `runtime.combat_mode` также допускает `disabled`, а `demo_reports` содержит только синтетические коды.

Метаданные содержат code/title, nullable времена отчёта, `visibility=public`, fights и actors. Смещения `start_ms/end_ms` относительно начала отчёта; `participant_ids=null` означает неизвестный состав конкретного боя, `[]` — подтверждённо пустой. Actors относятся к отчёту; игрок из общего списка не становится участником каждого боя автоматически. Известное неучастие даёт 400; отсутствие подтверждения участия и любых событий не выдаётся за нулевую эффективность.

Отсутствующий ресурс возвращает 202 с обычными Location/Retry-After/job ID. `/jobs/{id}` имеет kind `refresh_character|refresh_report|analyze_fight`. Public-only проверка, карантин и сроки БД обязательны перед выдачей. Доступность отчёта проверяется каждые 15 минут; после истечения проверки старый анализ не выдаётся. Максимум хранения — 24 часа. Подтверждённая недоступность даёт безопасный `REPORT_UNAVAILABLE` и каскадную очистку; неоднозначный 403 блокирует публикацию. Нет настройки источника — 503 `COMBAT_NOT_CONFIGURED`, без демофолбэка.

Анализ связан с code/fight/actor и версией отчёта в `meta.snapshot_id`. Метод `event-amounts/whole-fight-v1` делит сумму нормализованных исходящих damage/heal amount на всю длительность боя, не активное время. Healing amount определён контрактом как эффективное лечение; overheal хранится отдельно, доля равна overheal/(healing+overheal). Это собственный расчёт, не официальный рейтинг/percentile Warcraft Logs. Pet damage и события другого actor не приписываются игроку. Смерти считаются по target ID. Полнота потока и ограничение показываемого таймлайна разделены: `events_complete` и `timeline_truncated`.

Пагинация ограничена пятью страницами/10 000 событий. При неполном/некорректном потоке полные totals/rates/counts остаются null; подтверждённый полный пустой поток участника даёт нули. Отсутствующая сумма не становится нулём; неизвестная доля overheal остаётся null. Таймлайн содержит до 500 нормализованных наблюдений в хронологическом порядке, сохраняя последние контексты смертей. Агрегаты способностей относятся к полученным наблюдениям и при partial не обещают полную историю. Findings содержат Info/Unknown и индексы доказательств. Без проверенных правил rotation/cooldown/buff советы остаются Unknown; смерти не классифицируются как вина игрока.

Кеш не зависит от языка; смена нормализованных метаданных отчёта создаёт новую версию и отменяет прежние производные задания. Браузер отменяет старые запросы и проверяет code/fight/actor/version. При удалённом polling-задании однократно перечитывает исходный ресурс, чтобы получить его актуальный статус доступа.

## Внутренние проверки и совместимость

Health endpoints публикуются на отдельном внутреннем listener либо блокируются внешним ingress. OpenAPI `x-internal` сам по себе не является защитой. Liveness проверяет процесс; readiness — конфигурацию, совместимость схемы и PostgreSQL с короткими timeout. Redis может перевести API в `degraded` только при сохранении лимитов и гарантий PostgreSQL. Provider outage не должен запускать бесконечные рестарты приложения.

Данный контракт использует OpenAPI 3.1 / JSON Schema 2020-12; nullable описано через `type:[…,null]`/`anyOf`. Инварианты между `data`, `meta.status`, coverage, временными полями и job state проверяются контрактными тестами, включая случаи, которые переиспользуемые схемы не выражают полностью. Клиент игнорирует добавленные необязательные поля; сервер валидирует вход по опубликованной схеме. Удаление полей, изменение типов, семантики null, обязательности или значений enum требует нового major API либо согласованной миграции. Текущая локальная версия контракта — 0.6.0.

## Raider.IO

В режиме `RAIDERIO_ENABLED=true` маршруты персонажей и гильдий принимают регион EU/US, название или slug сервера и имя. При первом чтении возвращается `202` с задачей `refresh_raiderio`. После её выполнения `200` содержит нормализованный публичный снимок с `meta.source=raiderio`. Подтверждённое отсутствие ресурса даёт `404`. Ссылки на первоисточник хранят канонический сервер и имя. [Raider.IO Developer API](https://raider.io/api)

В профиле гильдии `members` содержит идентичность и наблюдаемые поля состава. `rankings` группирует места по рейду и сложности. `coverage` различает доступные, частичные и отсутствующие данные. При сравнении интерфейс загружает индивидуальные профили выбранных персонажей через GET. Сезон рейтинга Mythic+ отображается рядом со значением.

## Гильдии и сравнение (этап 5)

| Метод и путь | Поведение |
| --- | --- |
| `GET /api/v1/guilds/{region}/{realm}/{name}` | Профиль гильдии; `name` — канонический slug |
| `GET …/roster` | Состав из той же версии; `members:null` означает неизвестный состав |
| `GET …/analysis` | Сводка по разрешённым профилям с явным охватом |
| `POST /api/v1/refresh/guilds` | `{region,realm,name,locale?}`; 202, ограниченное фоновое обновление |
| `POST /api/v1/comparisons/characters` | `{characters:[{region,realm,name}],locale?}`; 200, от 1 до 5 разных ключей |

Slug гильдии проходит NFC и Unicode lowercase, 2–100 букв/цифр/диакритик/дефисов, без начального/конечного дефиса и начальной диакритики. Он не выводится из отображаемого имени. Ключи персонажей используют обычный NFC/casefold; повторы после нормализации отвергаются до чтения БД. POST принимает JSON до 8192 байт, не допускает неизвестные поля и trailing JSON; `force` не поддерживается.

Гильдия без снимка даёт 202 и `refresh_guild` job; разрешённый stale-снимок — 200 с обновлением в фоне. Успех job подтверждает постановку профилей участников, а не их загрузку. Состав обрабатывается пакетами до 50 и не обходит лимит очереди персонажей. Свежесть гильдии — 60 минут, срок выдачи — не более 30 дней. Обязательный 404 возвращает `GUILD_UNAVAILABLE`, удаляет данные и создаёт HMAC-negative на пять минут; 403 прекращает публикацию до перепроверки.

Анализ содержит `coverage` состава/профилей/секций, распределения классов/специализаций/подтверждённых ролей, mean/median item level с count, наблюдения зачарований/комплектов, охват прогресса и строки участников. Поля `role`, `notices`, item level и рейтинг nullable. Замечания — только Warning/Critical применимого ruleset; отсутствие применимости не становится нулём. Профиль обязан совпасть с участником по provider ID и каноническому ключу. Боевые логи не связываются по имени.

Сравнение выдаёт `entries` с отдельными status/reason/meta и шестью секциями, либо `data:null` для недоступной записи. `compatibility` содержит nullable `same_patch`, `same_specialization` (класс и spec), `mythic_plus_same_season` и `combat_comparable:false`; неизвестное значение не становится подтверждением или несовпадением. Недоступный профиль не уничтожает разрешённые элементы сравнения. Deadline ответа не позже каждого опубликованного входа. Агрегаты гильдии и сравнение не сохраняются отдельным долгоживущим кешем.

JSON-экспорт выполняется web-клиентом только после нового запроса с обычными проверками публикации. Свойства `runtime.demo_guilds` и `runtime.demo_comparisons` описывают только явно синтетические примеры; в live-режиме списки пусты.
