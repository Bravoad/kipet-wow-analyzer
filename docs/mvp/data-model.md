# Модель данных и фоновые обновления

Версия: 0.5 · 1 ноября 2026. Базовая модель MVP и реализованные расширения этапов 2–5.

Документ детализирует утвержденную архитектуру v1.0. [schema.sql](schema.sql) сохраняет исходный проект DDL этапа 1 и не заменяет применяемые [миграции](../../migrations). Реализация включает профиль, экипировку, характеристики, таланты, Rule Engine, Mythic+, рейдовый прогресс и отдельную подсистему публичных боевых отчётов. Этап 5 добавляет отдельную очередь гильдий, сводку состава и пакетное сравнение персонажей. Ниже правила исходной модели персонажа отделены от расширения боевых отчётов: его сроки и публикационные ограничения строже.

## Идентичность и нормализация

Внутренние UUID создает приложение. `characters.id`, `realms.id`, `character_snapshots.id` и `refresh_jobs.id` не совпадают с игровыми идентификаторами. Blizzard ID хранится отдельным nullable-полем до первой успешной загрузки. Ограничение уникальности только по Blizzard ID не вводим: оно не доказывает непрерывность личности между серверами и переносами.

Ключ поиска: `region + realm_id + name_normalized`. На старте разрешены `eu` и `us`. Каталог серверов возвращает канонические Blizzard `provider_realm_id` и `slug`. Connected realm хранится для справки и не заменяет конкретный сервер в ключе персонажа. Имя сервера из локализованного поиска сначала разрешается в запись каталога. Неоднозначное совпадение требует выбора сервера; случайный выбор запрещен.

`name_normalized` получает Unicode NFC → Unicode case folding → NFC; пробелы по краям пользовательского ввода убираются до проверки. Диакритика, кириллица и другие допустимые буквы не транслитерируются. Значения сравниваются без дополнительных accent-insensitive преобразований. URL-кодирование выполняется отдельно для каждого сегмента. SQL не пытается воспроизвести Unicode-нормализацию через `lower()`; один алгоритм выполняется в application-слое и тестируется на Unicode fixtures. Для внешнего запроса адаптер формирует lowercase character-name по требованиям поставщика отдельно от ключа case folding. Допустимый публичный ввод ограничен OpenAPI; запас хранения БД до 64 символов не расширяет API-лимиты и не утверждает игровой лимит имени. Управляющие символы, `/`, `\\` и URL-разделители отвергаются валидатором.

Публичный запрос допускает имя длиной 2–24 символа после NFC; нормализованный ключ после case folding ограничен 48 символами, поскольку преобразование может расширить строку. DDL допускает 1–64 символа для исходного имени и ключа как запас хранения, но application-валидация всегда применяет более узкие публичные границы. Импорт ответа провайдера проходит отдельную проверку и не открывает обход валидации пользовательского ввода.

Подтвержденное переименование внутри того же сервера можно отразить сменой имени существующей записи только при доказанном соответствии ответа summary исходному персонажу. Перенос и неоднозначное совпадение создают новую запись. Автоматического слияния истории между серверами нет. Если по тому же ключу приходит другой Blizzard ID, прикладная транзакция удаляет прежние снимки и начинает новую внутреннюю сущность; историю разных персонажей объединять нельзя.

Переход при несовпадении ID: worker в fenced-транзакции блокирует старое задание и identity, проверяет token и срок lease, удаляет старого персонажа со связанными снимками/заданиями, создает новый `characters.id` под тем же ключом поиска и новое `queued`-задание. Commit атомарен. Уже собранный payload отбрасывается и не публикуется. Если `provider_character_id` еще `null` у первоначального placeholder, первый подтвержденный ответ просто привязывает ID и не запускает замену. Для замены существующей сущности старое polling-задание исчезает: UI при `JOB_NOT_FOUND` однократно перечитывает профиль и следует новому job ID, если он появился; подтвержденный 404 завершает показ недоступностью. Такое восстановление ограничено одной попыткой, чтобы очистка/истечение jobs не создавали бесконечный цикл.

## Сущности и связи

| Таблица | Назначение и ключевые поля |
| --- | --- |
| `realms` | UUID, регион, ID и slug провайдера, локализованные имена, connected realm, время загрузки |
| `characters` | UUID, ключ поиска, display name, Blizzard ID, ссылка `current_snapshot_id`; null-ссылка означает еще не загруженный профиль; `publication_blocked_at/reason` изолируют данные при неоднозначном запрете доступа |
| `character_snapshots` | Неизменяемый снимок, источник, timestamps, версия нормализации, nullable patch/build/season, `refresh_job_id` для идемпотентности |
| `snapshot_sections` | Шесть строк `profile`, `equipment`, `statistics`, `talents`, `mythic_plus`, `raids`; полнота, собственные сроки актуальности и доступности, данные секции |
| `equipment_items` | Предмет по слоту и снимку, уровень, качество, чары, сокеты, характеристики и наблюдаемый бонус комплекта |
| `item_catalog` | Неидентифицирующие сведения о типе предмета; загрузка каталога не блокирует публикацию профиля |
| `talent_loadouts` | Наборы талантов, активность, специализация, nullable import/export string и выбранные узлы |
| `refresh_jobs` | Долговременная очередь, повторы, lease и fencing token |
| `provider_state` | Состояние провайдеров: реализованные общие gates `global` для Blizzard и Warcraft Logs, паузы и наблюдаемый остаток баллов WCL; дополнительные региональные/circuit-поля исходной модели не означают, что все такие механизмы задействованы; секретов нет |

Снимок строится в памяти и фиксируется одной транзакцией: header, шесть секций, дочерние строки, указатель текущего снимка, финальный статус задания. Неуспех не оставляет видимый полуготовый снимок. Старые снимки после фиксации не редактируются обычным обновлением. Исключение — обязательная очистка истекших/отозванных персональных данных, включая отдельные секции. Текущий снимок не означает гарантированную свежесть всех его частей.

Этап 3 хранит нормализованный прогресс внутри JSONB соответствующих секций. Отдельные таблицы прохождений из исходного проектного DDL пока не задействованы: приложение показывает лучшие наблюдаемые записи, а не накопленную историю. Миграция 0006 расширяет допустимые имена секций и добавляет старым снимкам `unavailable/never_fetched` без payload и времён получения. Отсутствующая секция при публикации получает то же состояние. Откат удаляет две секции и восстанавливает ограничение этапа 2.

Mythic+ имеет собственный nullable сезон; он не переносится в контекст Rule Engine. `run_scope` задаёт `season_best`, `current_period_best` либо `unknown`. Рейды хранят наблюдаемые дополнения, рейды, сложности и боссов, включая исторические. Nullable списки и счётчики сохраняют различие неизвестного, пустого и нуля. Обе секции имеют TTL 15 минут и самостоятельный максимальный срок хранения 720 часов; пригодность профиля остаётся обязательным условием выдачи. Кеш анализа рассчитывает сроки только по четырём исходным секциям.

DDL содержит ограничения форм и FK. Межстрочные инварианты — число секций, их полнота, совпадение character ID в задании и снимке, согласованность active spec — проверяются транзакционным repository API и интеграционными тестами. DDL намеренно не подменяет их триггерами.

## Содержимое секций

`state` описывает полноту, независимо от возраста: `complete`, `partial`, `unavailable`. `pending` используется в HTTP envelope для еще не загруженного результата; отдельного persisted snapshot с выдуманным профилем нет. `null` означает неизвестное значение; пустой массив означает подтвержденное отсутствие элементов. Неизвестное зачарование нельзя превращать в известный пустой список.

| Секция | Содержимое `snapshot_sections.payload` | Дочерние строки |
| --- | --- | --- |
| `profile` | Канонический identity, ID/локализованные названия класса, расы и специализации, faction, level, средний equipped item level, nullable время активности источника | Нет |
| `statistics` | Нормализованные значения характеристик с единицами (`rating`, `percent`, `amount`), nullable недоступные значения; secondary сохраняет разделение melee/ranged/spell | Нет |
| `equipment` | Наблюдаемые агрегаты: средний уровень, список полученных слотов, полнота ответа; без дублирования массива предметов | `equipment_items` |
| `talents` | Активная специализация и metadata полноты; без дублирования loadouts | `talent_loadouts` |

`payload` — внутреннее представление, а не прямой JSON-ответ Blizzard или REST. Repository собирает транспортную модель из секции и дочерних строк. В HTTP используются поля и названия из OpenAPI; SQL-колонки не являются публичным контрактом. JSONB позволяет сохранить нормализованные optional-поля при изменениях игровой схемы, но адаптер проверяет их типы до записи.

В `statistics.secondary` поля `critical_strike` и `haste` содержат отдельные nullable `melee`, `ranged`, `spell`; значения не сворачиваются в один произвольный процент. `mastery` содержит `rating` и `percent`, `versatility` — `rating`, `damage_done_percent`, `healing_done_percent`, `damage_taken_reduction_percent`. Каждый недоступный показатель nullable. Проценты выражаются в процентных пунктах; рейтинг и процент не заменяют друг друга. Окончательные типы чисел и вложенных объектов определяет OpenAPI.

Для каждого предмета храним наблюдаемый slot от провайдера, item ID, item level, качество и тип экипировки. Slot не ограничивается в DDL вечным перечнем: новый допустимый slot адаптер может сохранить как неизвестный для анализатора без потери предмета. `enchantments_state`/`sockets_state = unknown` требуют `null`; `known` требуют массив, включая `[]`. Сокет содержит тип и nullable вставленный предмет; модификаторы, bonus IDs и характеристики нормализуются без догадок о BiS. `set_info` хранит только наблюдаемые данные, не трактует отсутствие поля как отсутствие комплекта.

Набор талантов содержит specialization ID и узлы `(tree_type, node_id, rank, choice_id?)`. `nodes_state` различает отсутствующие данные (`selected_nodes = null`, REST `nodes = null`) и подтвержденный пустой список (`[]`). `provider_loadout_id` может отсутствовать; внутренний UUID остается доступен. `is_active` имеет три состояния: `true` — подтвержденный активный, `false` — подтвержденный неактивный, `null` — активность неизвестна. Подстановка `false` по умолчанию при неполных данных запрещена; доступные узлы такого loadout сохраняются. Partial unique index разрешает не более одного подтвержденного активного loadout на снимок, не ограничивая количество неизвестных. Неактивные loadouts разных специализаций допустимы. Отсутствие текущего набора правил не мешает показать таланты и не создает оценку билда.

Локализованные игровые названия храним объектом, например `{"en_US":"Example","ru_RU":"Пример"}`. Если перевод не получен, UI показывает доступное название с явным fallback; ID остается основой связи. Имя персонажа не переводится. Сырые внешние ответы не попадают в постоянную БД и логи по умолчанию. Contract fixtures анонимизируются отдельно.

Каталоги серверов и предметов планово переполучаются раз в 24 часа; их исходный `fetched_at` не продлевается чтением из кеша. Стартовый предельный возраст также 720 часов. Просроченный каталог нельзя выдавать через API, а его очистка учитывает FK: связанные identity сначала должны быть перепроверены/перепривязаны к заново полученной записи либо удалены по политике данных. Нельзя обходить deadline сохранением старых localized names в бессрочном справочнике.

## Боевые отчёты: реализованное расширение этапа 4

Миграция 0007 создаёт четыре отдельные таблицы; очередь персонажей и её публикационный протокол сохраняются. Ключ отчёта — непрозрачный регистрозависимый код из 16 ASCII букв/цифр. Fight ID и actor ID локальны для этого отчёта и не равны Blizzard ID или внутреннему UUID персонажа. Совпадение имени не связывает записи автоматически.

| Таблица | Назначение и ограничения |
| --- | --- |
| `combat_reports` | Код, UUID версии нормализованных метаданных, nullable payload/timestamps до первой загрузки, marker карантина; payload содержит только явно публичный отчёт |
| `combat_analyses` | UUID расчёта, FK на код отчёта с каскадным удалением, версия метаданных, fight/actor ID, нормализованный результат и собственные сроки; unique по report/version/fight/actor |
| `combat_jobs` | Отдельная долговременная очередь; `(fight_id,actor_id)=(0,0)` загружает метаданные, положительные ID рассчитывают бой; partial unique index допускает одно активное задание на code/fight/actor |
| `combat_negative_lookups` | HMAC от кода с отдельным префиксом домена и сроком 5 минут; без самого кода, payload или прежнего результата |

Источник отдельно закрепляется ключом `combat_provider_mode` в `app_settings`: fixture и warcraftlogs не смешиваются. Режим disabled не выдаёт накопленные данные и не заменяется синтетическим источником. Секреты OAuth хранятся в серверной конфигурации, не в этих таблицах и не в browser. HTTP читает PostgreSQL и ставит задания; внешние GraphQL-запросы выполняет worker.

Нормализованные метаданные содержат бои и actors отчёта. Nullable `participant_ids` каждого боя отражает явный состав от источника: null — неизвестен, [] — подтверждённо пуст. Игрок из общего списка actors не считается участником каждого боя. Известное неучастие запрещает расчёт; при неизвестном составе события могут подтвердить присутствие, но пустой поток не доказывает нулевую активность. Отсутствующие списки fights/actors дают partial coverage, а явно пустые остаются известными.

Каждая загрузка метаданных и каждая страница событий требуют совпадения кода и явной публичности отчёта. Private, unlisted и неизвестная visibility не публикуются. После подтверждённой недоступности отчёт удаляется вместе с расчётами и заданиями через FK; HMAC-запись подавляет повторную загрузку на 5 минут. Неоднозначный 403/известный GraphQL access denial ставит карантин до успешной перепроверки. Ошибка учёта квоты не маскирует уже известный отказ доступа.

Проверка публичной доступности свежа 15 минут; после этого чтение ждёт фоновой проверки, даже если 24-часовой предельный срок хранения ещё не истёк. Отчёт и расчёт не выдаются из старого кеша в обход карантина или этой проверки. Дедлайны анализа дополнительно ограничены сроками отчёта. Maintenance удаляет истёкшие отчёты, их дочерние записи и неактуальные версии анализа; терминальные задания хранятся не дольше 24 часов, отрицательные записи — до своего срока. Эти значения — реализованные пределы проекта, не утверждение об условиях Warcraft Logs.

Версия отчёта меняется, когда изменились его нормализованные метаданные. Такая транзакция удаляет прежние расчёты и отменяет активные производные задания. Успешная перепроверка неизменившихся метаданных сохраняет UUID версии, но не продлевает собственные сроки ранее рассчитанного анализа. Публикация анализа заново проверяет текущую версию, публичность, карантин, сроки и действующую lease. Потерявший lease worker не может записать результат или снять карантин; финальная guarded-проверка срока не позволяет commit после истечения lease внутри медленной транзакции.

Combat jobs используют те же публичные состояния, что и задания профиля, но имеют kind `refresh_report` или `analyze_fight`. Захват использует короткую транзакцию и `FOR UPDATE SKIP LOCKED`; lease — 60 секунд, heartbeat — 15 секунд, максимум — 5 фактических попыток. Worker получает общий budget permit до увеличения attempts; ожидание квоты не расходует попытку. `Retry-After` не сокращается локальным backoff. В `provider_state` Warcraft Logs имеет собственный global gate и наблюдаемые `budget_remaining/budget_resets_at`: неизвестные баллы не превращаются в ноль, известное исчерпание блокирует запросы до сброса. Позднее наблюдение не пополняет ещё не истёкший бюджет. Учёт баллов не обещает заранее известную стоимость произвольного GraphQL-запроса; запросы фиксированы кодом.

События собираются в памяти ограниченной пагинацией: до 5 страниц по 2000 событий. В БД сохраняется результат с методикой, полнотой, агрегатами способностей, findings и нормализованным таймлайном, не сырой ответ провайдера. `event-amounts/whole-fight-v1` делит суммы исходящих amount точного actor на всю длительность боя; урон питомцев и других actors не присоединяется, смерти определяются по target ID. Нормализованный контракт считает heal amount эффективным лечением, overheal — отдельной величиной. Пустой полный поток подтверждённого участника даёт нули; неполный поток оставляет полные totals/rates/counts null. Неизвестные суммы и доли остаются null. Флаг `timeline_truncated` отдельно отмечает сокращение показываемых наблюдений до 500; это не то же самое, что неполная загрузка исходного окна. При сокращении сохраняются последние контексты смертей и хронологический порядок.

Итог не является рейтингом Warcraft Logs или оценкой качества игрока. Без проверенных правил рекомендации о ротации, доступных cooldown и buff uptime остаются Unknown. Все текущие боевые fixtures синтетические; живая GraphQL-схема и семантика amount требуют приёмки по обезличенным реальным ответам с credentials. Полнота локальных тестов не подтверждает точность непроверенных live-результатов.

## Свежесть, доступность и срок жизни персонажа

| Параметр | Начальное значение | Значение |
| --- | --- | --- |
| Profile/equipment/statistics freshness | 15 минут | Настраиваемый интервал до запуска фонового обновления |
| Talents freshness | 30 минут | Собственная граница секции |
| Negative lookup cache | 5 минут | Только после подтвержденного отсутствия профиля |
| Максимальный возраст персональных данных | 720 часов | Политика проекта; не заявление о действующей редакции условий Blizzard |
| Плановая проверка доступности | До 27 суток после последней проверки | Резерв до hard deadline; распределяется по времени |
| Очистка истекших данных | Каждый час | Read-path скрывает данные немедленно по deadline, не ждет очистки |

Все интервалы конфигурируются. На старте увеличение максимального возраста выше 720 часов запрещено без отдельного пересмотра политики. До публичного запуска ответственный проверяет актуальные условия поставщика. Этот документ фиксирует консервативное проектное поведение, а не юридическое толкование.

`fetched_at` — момент успешного получения данных нашим сервером. `source_updated_at` — nullable время, которое сообщил источник; это другое понятие. `profile_verified_at` устанавливается только после успешной проверки summary. `fresh_until` определяет fresh/stale; `valid_until` — предельную допустимость выдачи. Тimestamps вычисляет сервер, пользователь не может их задавать.

Каждая секция хранит собственные `fetched_at`, `fresh_until`, `valid_until`. При недоступности equipment или talents допускается перенести еще разрешенную старую секцию в новый снимок, сохранив ее исходные timestamps. Успешная загрузка profile не делает старую экипировку свежей и не продлевает ее retention. `checked_at` отражает новую попытку, `error_code` — безопасную причину; coverage отдельно остается основанным на фактически доступных данных.

Выдача разрешена только если актуальны hard deadlines header/profile и запрошенной секции. Секция с истекшим `valid_until` скрывается и очищается вместе с ее дочерними строками. Обновление profile при неизменившемся remote last-modified не продлевает срок хранения непереполученных секций. Сырые conditional responses обрабатываются адаптером только при доказанной валидности исходного payload и соблюдении собственного hard limit; они не дают бесконечной истории.

Планировщик повторной проверки нужен для уже отслеживаемых профилей, даже если их никто не открывает. Просроченный placeholder без успешного профиля и связанные задания очищаются по тому же верхнему пределу. Терминальные задания можно удалять раньше (начальное предложение: 24 часа после завершения); постоянного архива поисков нет.

## Недоступность и удаление

Подтвержденный `404` канонического character summary скрывает и удаляет персонажа, его снимки, экипировку, таланты и задания одной транзакцией через `ON DELETE CASCADE`. Удаление отдельной equipment/talents секции провайдером не доказывает исчезновение всего персонажа: соответствующая секция становится unavailable, профиль остается.

`401/403`, `429`, timeout, сетевые ошибки, неверный namespace/realm и ошибки JSON-схемы не классифицируются как подтвержденное отсутствие. При временных ошибках разрешен stale только в пределах hard deadlines и при отсутствии запрета публикации. Неоднозначный `403` summary устанавливает `characters.publication_blocked_at` и `publication_block_reason = provider_access_denied` в fenced-транзакции до ответа. Он блокирует выдачу всех данных персонажа до успешной серверной перепроверки summary; старый Redis payload не обходит карантин. Успешная повторная проверка снимает запрет одновременно с фиксацией нового снимка. `403` необязательной секции блокирует ее выдачу, не удаляет весь профиль и не разрешает перенос старого payload этой секции.

Публикационный read-path сверяет существование персонажа, отсутствие quarantine marker, текущий snapshot ID и его дедлайны в PostgreSQL до возврата Redis payload. Это делает удаление fail-closed даже при сбое Redis. Ключ включает snapshot UUID; неавторизованный старый ключ не становится самостоятельным источником правды. При недоступной БД персональные данные не выдаются из Redis. После commit удаления кеши инвалидируются best-effort; просроченные ключи дополнительно исчезают по TTL. В HTTP нельзя разрешать самостоятельный долгий публичный/CDN-кеш идентифицируемых payload, обходящий этот контроль.

Отрицательный кеш — HMAC от канонического ключа, код отсутствия и TTL 5 минут; без имени и старого payload. Это средство экономии запросов, а не вечная tombstone-таблица. Завершенный worker не может воскресить удаленные данные: публикация требует живого задания, соответствующей lease и существующего `character_id`.

Очистка истории удаляет старые snapshot rows после переключения `current_snapshot_id` либо обнуления, если текущий истек. До удаления snapshots очищается/переназначается current pointer в той же транзакции. Аналитические результаты будущих этапов также должны иметь каскадный FK и собственный deadline, не позднее исходных данных. Резервные копии требуют ограниченного retention и повторного применения записей удаления перед восстановлением публичного сервиса; конкретный backup retention определяется операционным бюджетом.

## Надежная очередь PostgreSQL

Redis ускоряет кеш и общие лимитеры. Корректность очереди и подавление дубликатов обеспечиваются PostgreSQL: partial unique index допускает только одно активное задание на персонажа в `queued`, `running` или `retry_wait`.

| Статус | Переходы |
| --- | --- |
| `queued` | `running`, `cancelled` |
| `running` | `succeeded`, `retry_wait`, `failed`, `cancelled` |
| `retry_wait` | `running`, `cancelled` |
| `succeeded`, `failed`, `cancelled` | Терминальные; новый refresh создает новый ID |

Создание placeholder и задания выполняется одной короткой транзакцией. Вставка использует conflict handling по partial unique index и возвращает ID уже активного задания. Параллельные первые запросы сериализуются по существующей строке персонажа; после конфликтующей вставки read выполняется новым statement с актуальным snapshot видимости. Отдельная Redis-lock не требуется для доказательства уникальности.

Захват задачи выполняет короткая транзакция с `FOR UPDATE SKIP LOCKED`, сортировкой `priority DESC, run_after, created_at, id` и проверками `run_after <= clock_timestamp()` и `attempts < max_attempts`. В ней worker назначает новый случайный `lease_token`, `lease_owner`, `leased_at` и `lease_until`, затем commit. После получения quota permit он увеличивает `attempts` guarded-обновлением с token и действующей lease непосредственно перед фактической попыткой сбора summary. Ожидание лимитера без исходящего запроса не расходует попытку; если пауза длинная, job возвращается в `retry_wait` с очищенными lease-полями. Внешние HTTP-вызовы выполняются после снятия блокировки. Начальное предложение: lease 60 секунд, heartbeat каждые 15 секунд, тайм-аут отдельного HTTP-вызова 10 секунд, deadline всего сбора 120 секунд. Это конфигурация, а не фиксированная возможность провайдера.

Heartbeat, повтор, отмена и финальная запись обязаны предъявить текущий token. Пример финального fencing-протокола:

1. Начать транзакцию; заблокировать строку job через `SELECT ... FOR UPDATE`.
2. Проверить `status = running`, совпадение token и `lease_until > clock_timestamp()`; иначе rollback без записи данных.
3. Заблокировать соответствующего character, проверить его существование и каноническую идентичность ответа.
4. Создать snapshot+sections+children, обновить текущий указатель, перевести job в `succeeded`, очистить lease-поля и установить `finished_at`.
5. Проверить срок lease повторно в guarded финальном UPDATE; если он истек — rollback всей транзакции. Commit делает данные и статус видимыми одновременно.

`character_snapshots.refresh_job_id UNIQUE` дополнительно не допускает второй снимок для одного задания. При неопределенном результате commit worker сначала перечитывает job: `succeeded` означает завершение без повторной публикации. Все mutation-пути берут блокировки в порядке job → character. Purge забирает связанные job rows в стабильном порядке, затем character. Для массовых операций применяется единый порядок UUID; возможные deadlocks повторяются ограниченно.

Reaper захватывает истекшие running jobs через `SKIP LOCKED`, аннулирует старый token и переводит задание в `retry_wait`, либо `failed`, когда attempts исчерпаны. Старый worker после выдачи новой lease не сможет записать результат. После рестарта очереди ничего не теряется; семантика доставки at-least-once, публикации результата — идемпотентная.

Начальное предложение: максимум 5 фактических попыток сбора включая первую, full jitter с базой 2 секунды и экспоненциальным ростом до 5 минут. Для `429` учитывается provider `Retry-After`: дата `run_after` не раньше указанной, без удержания worker в sleep. Общая пауза сохраняется в `provider_state`; получение quota permit производится атомарно. Неизвестный лимит задается консервативной конфигурацией и наблюдается в метриках, не выдумывается из числа пользователей. На постоянный `400`/schema mismatch бесконечных повторов нет; `401` допускает один сброс OAuth-token до типизированного отказа. `404` summary запускает purge. Неуспех секций дает partial snapshot и безопасные причины вместо полного отката доступного профиля, когда соблюдены инварианты.

Стартовые 2 запроса/с и burst 2 относятся ко всему приложению, всем регионам и репликам суммарно. `provider_state` содержит обязательную строку `(blizzard, global)` и дополнительные `(blizzard, eu/us)` для региональных пауз и квот. Permit проверяет общий gate и нужный региональный gate в одной транзакции; строки блокируются в порядке global → region. `budget_remaining` и `budget_refilled_at` позволяют пересчитать token bucket под блокировкой, `next_allowed_at` учитывает `Retry-After`. При ожидании ни одно региональное разрешение не обходится. Авторизационные запросы, загрузки каталогов и повторные HTTP-запросы также учитываются общим исходящим лимитером; региональные ограничения могут быть строже. Redis может ускорять механизм, но fallback не создает независимые 2 RPS на каждую реплику или регион.

Идемпотентность не означает бесконечный пользовательский refresh: новый запрос после terminal job подчиняется cooldown и rate limit. Проектные пределы на пользователя, глобальную очередь и число workers настраиваются независимо.

## Приёмка схемы

Базовый DDL этапа 1 проверяется отдельно от актуальных миграций. Для миграций нужны чистый запуск, заполненная база и контролируемый откат; для поведения — два конкурентных enqueue, expired lease+late commit, повтор после неопределённого commit, смена специализации, неполная экипировка, stale equipment при fresh profile, повторное использование имени другим ID, удаление персонажа с current snapshot и истечение отдельной секции. Этап 4 дополнительно проверяет версию отчёта, public-only доступ, карантин/purge, отдельную очередь и 24-часовой deadline. Индексы должны подтверждаться планами запросов на реалистичных fixtures, а не одной заявленной целью RPS. Этот документ не подменяет результаты конкретного прогона, live-приёмку источника и нагрузочные измерения.

## Гильдии и сравнение: реализованное расширение этапа 5

Миграция 0008 добавляет `guilds`, `guild_snapshots`, `guild_jobs`, `guild_negative_lookups`. Ключ гильдии — регион, realm и канонический slug; provider ID не заменяет внутренний UUID. Смена provider ID очищает прежнюю идентичность. Неизменяемый JSONB-снимок включает профиль и состав, fresh_until +60 минут, valid_until не позже +720 часов. Неизвестный состав отличается от пустого списка.

Очередь гильдий хранит собственные lease/token/attempts и cursor 0–1000. Запись снимка и публикационного указателя требует действующей lease. Постановка профилей участников идёт пакетами до 50 под блокировкой задачи гильдии и общим admission lock очереди персонажей. Курсор и поставленные задачи коммитятся вместе. При заполненной очереди курсор сохраняется, попытка ожидания не требует нового сетевого сбора. Перезапуск продолжает опубликованный состав. Прежний token не может продвинуть курсор после выдачи новой lease.

Подтверждённый обязательный 404 удаляет гильдию, снимки и её задачи; отрицательный ключ HMAC живёт пять минут. Карантин 403 запрещает выдачу профиля, состава и производной сводки. Удаление гильдии не удаляет независимо загруженные профили персонажей. Maintenance и фильтры чтения соблюдают собственные сроки гильдии.

`FindMany` получает ограниченный массив ключей и одним SQL-запросом возвращает выровненные текущие записи, секции, задания и negative-флаги. Сравнение ограничено пятью ключами; сводка гильдии — 1000 участниками. Публикация дополнительно проверяет карантин, срок идентичности, каталога realm, обязательного профиля и каждой секции. Частично просроченные секции остаются null, остальные разрешённые данные могут отображаться. Производные сводки считаются на чтении и не получают отдельного срока сверх исходных данных.
