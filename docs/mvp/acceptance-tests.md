# Приёмочные сценарии

## Эксплуатационная подготовка шестого этапа

| ID | Условие | Ожидаемый результат |
| --- | --- | --- |
| O01 | Ledger пуст/неполон/изменён или содержит будущую миграцию | Startup/readiness не принимают схему; проверка не меняет ledger |
| O02 | Worker-компонент не запущен, завершился или начат shutdown | Readiness снимается; внешний доступ к listener отсутствует |
| O03 | Metrics не могут подтвердить схему/БД | 503 и scrape_success=0; старые значения не выглядят новым scrape |
| O04 | Некорректный или неизвестный пользовательский URL | HTTP labels содержат шаблон либо unmatched, без имени/IP/query |
| O05 | Превышен API/gateway body limit | Типизированный JSON 413, UUID, no-store; нет HTML вместо контрактной ошибки |
| O06 | Включён локальный мониторинг | Обе цели собираются, dashboard provisioned, панели не требуют публичных внутренних портов |
| O07 | Короткий bounded load | Настоящий limiter даёт отдельно учтённые 429, неожиданные сбои не скрываются |
| O08 | Восстановлена изолированная fixture-копия | Deadline/карантин сохраняют приоритет над restored payload; рабочая БД не изменена |

Результаты локальных проверок и оставшиеся условия публичного запуска — в [отчёте подготовки релиза](../operations/release-validation.md).

Версия: 0.5 · 1 ноября 2026. Матрица базового MVP и реализованных расширений этапов 2–5. Приложение и исполняемые тесты существуют; эта матрица задаёт ожидаемое поведение, а не объявляет каждый сценарий пройденным на реальном источнике.

Первый этап включает публичный поиск и профиль персонажа, экипировку, характеристики, таланты, PostgreSQL, Redis, Blizzard OAuth и фоновое обновление. Рабочие регионы: EU и US; интерфейс: русский и английский. Этапы 2–5 добавляют Rule Engine, Mythic+, рейдовый прогресс и публичные боевые отчёты. Добавлены гильдии, сравнение до пяти персонажей и JSON-экспорт. Синтетические проверки подтверждают поведение локальной реализации, а live-контракты Blizzard/Warcraft Logs требуют отдельной приёмки с credentials.

Точные DTO и коды ошибок задают [OpenAPI](../../api/openapi/mvp-v1.yaml) и [контракт API](api-contract.md). SQL-инварианты описаны в [модели данных](data-model.md). Этот набор проверяет наблюдаемое поведение, а не конкретный способ реализации.

## Условия проведения

- Управляемые часы, предсказуемый планировщик и управляемый адаптер провайдера позволяют проверить TTL, backoff и истечение lease без реальных ожиданий.
- Внешний адаптер заменяется контролируемым сервером для 200/401/403/404/429/5xx, тайм-аутов и повреждённых ответов. Секреты и токены используются только тестовые.
- Для транзакций, уникальных ограничений, очереди и удаления используется настоящий PostgreSQL в изолированном тестовом окружении; для кеша — Redis с возможностью отключения.
- JSON-примеры, события и нормализованные снимки до получения проверенных ответов Blizzard/Warcraft Logs маркируются `synthetic`. Они не являются контрактными fixtures реального источника.
- Числовой TTL берётся из конфигурации: исходные проектные значения — 15 минут для профиля, экипировки и характеристик, 30 минут для талантов. Предел допустимого возраста задаёт политика хранения; первоначальный проектный предел — 30 дней для каждой секции. Это проектное ограничение, а не утверждение о действующей редакции юридических условий API.

| ID | Дано | Когда | Тогда |
| --- | --- | --- | --- |
| P01 | Данных нет; адаптер доступен | Запрошен валидный персонаж | API создаёт одно задание, возвращает `202`, `data:null`, `status:pending`, `Location` и `Retry-After`; HTTP-обработчик не вызывает Blizzard напрямую |
| P02 | Задание P01 успешно завершилось | Клиент повторяет GET профиля | `200`, профиль и метаданные источника, времени и покрытия; UUID отделён от игрового ID; нет токенов и сырого ответа провайдера |
| P03 | Профиль допустим и свеж | Выполнено много GET | `200`, `status:fresh`; новые задания и внешние вызовы отсутствуют |
| P04 | Профиль прошёл `fresh_until`, но ещё допустим | Выполнен GET | `200`, `status:stale`, достоверный возраст; обновление ставится один раз, допустимые данные доступны во время обработки |

| P06 | Секция частично нормализована | GET секции | Известные поля возвращаются, неизвестные явно отсутствуют/равны `null` по DTO; coverage `partial`; нет подстановки нулей и пустых списков |
| P07 | Ввод содержит неподдержанный регион, превышение длины или запрещённые символы | Поиск либо refresh | `400` с полями валидации; нет постановки задания и внешнего запроса |

| P10 | Профиль перенесён или переименован; у источника новый идентификатор | Найден новый адрес профиля | Нет автоматического объединения записей по имени или предположению о сохранении Blizzard ID; прежний адрес обрабатывается по отдельной проверке доступности |
| P11 | Найден realm не в выбранном регионе либо неоднозначное отображаемое имя | Выполняется поиск | Нет молчаливого выбора другого сервера; требуется разрешённый канонический realm по правилам API |
| P12 | Есть много серверов; список запрашивается с фильтром, языком и курсором | Клиент листает каталог | Порядок и курсор устойчивы для контекста запроса; лимит соблюдён; повреждённый/чужой курсор отклонён; регионы не смешиваются |

## Провайдер, ошибки и завершение ожидания

| ID | Дано | Когда | Тогда |
| --- | --- | --- | --- |
| E01 | Есть ранее допустимый снимок | Подтверждённый ответ summary персонажа — `404` | Данные сразу перестают отображаться; GET возвращает `404 CHARACTER_UNAVAILABLE`; снимки, секции, производные результаты и кеш очищаются по процедуре удаления |
| E02 | Summary доступен | Equipment, statistics или talents endpoint отвечает `404`/не предоставляет секцию | Только секция становится `unavailable` с безопасной причиной; весь персонаж не удаляется, `404` секции не приравнивается к summary `404` |
| E03 | Есть ранее полученные данные | Summary отвечает неоднозначным `403` | Профиль и его секции скрываются в quarantine, `502 PROVIDER_ACCESS_DENIED`; публичный ответ не утверждает удаление/существование; удаления по одному такому сигналу нет |
| E04 | Summary доступен | Optional-секция отвечает `403` | Скрыта только недоступная секция; её старые данные не показываются; остальной профиль остаётся доступен |
| E05 | OAuth-токен просрочен | Источник возвращает `401` | Разрешено одно серверное обновление токена в рамках попытки; при повторном `401` — `502 PROVIDER_AUTH_FAILURE`, без purge, утечки токена и бесконечного цикла |
| E06 | Провайдер возвращает `429` с `Retry-After` | Worker обрабатывает ответ | Задание уходит в `retry_wait`, следующая попытка не раньше допустимого времени; общий бюджет провайдера соблюдён всеми workers |
| E07 | Источник недоступен либо превышен тайм-аут | Выполняется обновление | Допустимые stale-данные остаются явно помеченными; при активной попытке без профиля допустим `202`; после окончательного отказа — `503 PROVIDER_UNAVAILABLE`; повторы ограничены, с backoff и jitter |
| E08 | Источник возвращает повреждённый JSON, неправильный тип или несовместимую структуру | Адаптер нормализует ответ | Не публикуется ошибочный/нулевой снимок; ошибка адаптера наблюдаема, допустимый старый снимок не затирается; после окончательного отказа без допустимых данных — безопасный `502 PROVIDER_INVALID_RESPONSE` |
| E09 | Повторы исчерпаны | Клиент опрашивает `/jobs/{id}` | `200`, состояние `failed` и безопасная причина; frontend прекращает polling, показывает окончание попытки и допустимый способ повторить позже |
| E10 | Последняя попытка завершилась окончательным отказом; cooldown ещё действует | Клиент снова открывает профиль без допустимого снимка | `502` либо `503` по причине отказа; не создаётся новый job на каждый GET и не возвращается бесконечный pending |
| E11 | Задание успешно выполнилось | Клиент опрашивает job | `200`, `succeeded`; клиент повторяет GET ресурса, а не ждёт профиль в job payload |
| E12 | Неизвестный или некорректный UUID задания | Выполнен GET job | Безопасный `404` либо `400` соответственно; нет перечисления чужих payload, токенов или произвольных внутренних ошибок |
| E13 | Frontend опрашивает задание старого персонажа, удалённое при замене идентичности; API отвечает `404 JOB_NOT_FOUND` | Обрабатывается исчезновение задания | Старый polling прекращается; выполняется ровно один recovery GET исходного профиля в рамках этого потока: при `202` клиент следует новому `job_id`, при `200` показывает допустимые данные, при подтверждённом `404` скрывает профиль, при окончательной ошибке показывает её; старое задание повторно не опрашивается, повторяющиеся `JOB_NOT_FOUND` не запускают бесконечную цепочку recovery GET |

## Очередь и согласованность

| ID | Дано | Когда | Тогда |
| --- | --- | --- | --- |
| Q01 | Данных нет либо они устарели | Одновременно приходят 100 GET/POST refresh одного нормализованного ключа | В PostgreSQL не более одного активного задания на ключ; ответы ссылаются на него; повторная доставка не создаёт дубли снимков |
| Q02 | Два workers выбирают задачи | Они одновременно захватывают очередь | Одна задача имеет одного действующего владельца lease; другие задачи могут обрабатываться независимо; внешние вызовы не удерживают долгую SQL-транзакцию |
| Q03 | Worker A потерял lease; worker B перехватил задачу и сохранил результат | A поздно завершает внешний запрос | Fencing-проверка запрещает A менять snapshot pointer, job и кеш; новый результат не затирается старым |
| Q04 | Worker завершился между внешним ответом и commit | Истёк lease и job получен повторно | Повтор идемпотентен: один принятый результат, согласованные snapshot pointer и состояние задания |
| Q05 | Commit состоялся; процесс умер до ответа или обновления Redis | Job доставлен повторно либо клиент читает профиль | PostgreSQL сохраняет согласованное состояние; повтор не создаёт другой принятый результат; кеш восстанавливается без потери корректности |
| Q06 | Снимок содержит прежнюю специализацию | Успешно загружена новая специализация | Новый неизменяемый снимок становится текущим атомарно; прежние таланты и результаты не выдаются как относящиеся к новой специализации |
| Q07 | Summary обновлён, equipment не удалось получить | Worker завершает попытку | Покрытие equipment отражает реальную недоступность/допустимое переиспользование по контракту; его `fetched_at` и `valid_until` не заменяются временем нового summary |
| Q08 | Redis недоступен | API читает данные и создаёт refresh | Чтение и дедупликация корректно работают через PostgreSQL; если общий лимитер провайдера недоступен и безопасного fallback нет, внешние запросы приостановлены, а не отправлены без лимита |
| Q09 | После удаления осталась старая запись Redis или поздний writer | GET либо позднее обновление кеша | Скрытый профиль не воскресает; проверка доступности/поколения и процедура инвалидирования имеют приоритет над кешем |
| Q10 | Статус задания `cancelled` | Frontend получает его при polling | Ожидание прекращается; новое задание создаётся только при разрешённом новом запросе, без автоматического бесконечного повтора |
| Q11 | У текущей записи по тому же нормализованному ключу уже известен Blizzard ID; проверенный summary содержит другой Blizzard ID | Действующий worker обрабатывает замену идентичности | Одна fenced-транзакция удаляет прежние character, snapshots, производные данные и jobs, создаёт новый внутренний UUID и новое задание `queued`; payload старого персонажа не публикуется и не переносится в новый; старый job возвращает `404 JOB_NOT_FOUND`; поздний worker и старый Redis-кеш не восстанавливают удалённые данные; дальнейшее поведение клиента соответствует E13 |

## Условия рекомендаций второго этапа

Следующие проверки относятся к [спецификации правил](analysis-rules.md) и реализованному endpoint анализа. Наличие endpoint не означает наличия проверенных игровых рекомендаций для каждого контекста.

| ID | Дано | Когда | Тогда |
| --- | --- | --- | --- |
| R01 | Нет проверенного набора правил либо эталона талантов | Запрошена оценка | `Unknown` с причиной; профиль/таланты можно показать; нет снижения балла, выдуманных советов и подбора ближайшего патча |
| R02 | Поле зачарований отсутствует, а не подтверждённо пусто | Исполняется `GEAR_MISSING_ENCHANT` | `Unknown`, предупреждение об отсутствии зачарования не создаётся |
| R03 | Предмет не подходит под проверяемое зачарование | Исполняется правило | `not_applicable`; случай исключён из числа выполненных/невыполненных игровых проверок |
| R04 | Эталон включает допустимую альтернативу таланта | Сборка использует эту альтернативу | Нет ложного `Warning`; результат совпадает с правилами эквивалентности |
| R05 | Различия талантов есть, доказанного нарушения нет | Выполняется сравнение | `Info` с конкретными отличиями и контекстом; не утверждается потеря DPS |
| R06 | Новый патч, сезон либо специализация несовместимы с прежним ruleset | Открывается прежний результат | Он не применяется к новому контексту; нужен новый подтверждённый ruleset/пересчёт |
| R07 | Снимок, контекст и ruleset неизменны; язык меняется | Повторяется оценка | Содержательный результат и доказательства стабильны; меняется только локализованный текст |

## Критерии готовности реализации

Для завершения первого этапа должны пройти P/E/Q/D/U-сценарии на выбранном окружении, контрактная валидация OpenAPI и нормализации, миграции на пустой БД и проверка конкурентного доступа. Значимые конкурирующие операции проверяются Go Race Detector; проверки транзакций и уникальности выполняются в PostgreSQL. Полный production security-аудит и нагрузочная квалификация относятся к шестому этапу и не считаются выполненными этими сценариями.

Результат прогона должен содержать версию исходников, конфигурацию TTL/лимитов без секретов, типы fixtures, версии PostgreSQL/Redis и фактические pass/fail. Цели архитектуры p95, RPS и доступности становятся подтверждёнными только после измерений на описанном оборудовании; здесь результаты измерений не заявлены.

Первые проверки правил R01–R07 и синтетические наборы должны пройти перед включением рекомендаций второго этапа. Ветви применимости и исключений проверяются отдельно от процента покрытия.

Расширения этапов 3–4 проверяются сценариями M/C на изолированных synthetic-данных и реальной PostgreSQL. Их успешный локальный прогон не означает приёмку текущих схем Blizzard/Warcraft Logs или точности непроверенной live-семантики amount. Для такой приёмки требуются серверные credentials, обезличенные ответы источника и подтверждённые ожидаемые расчёты.
