# Эксплуатационная подготовка: локальный результат

1 ноября 2026 года. API 0.6.0. Это локальная подготовка шестого этапа утверждённой архитектуры. Публичный production-релиз не выполнялся.

## Найденные и исправленные проблемы

Холодное сравнение использовало `comparison_read`, которого нет в SQL-ограничении причин задания. Незагруженные персонажи могли получить инфраструктурную ошибку вместо постановки в очередь. Теперь используются обычные `cache_miss`/`stale_read`. PostgreSQL-тест проверяет два холодных ключа, реальные queued jobs и повторное чтение без дубликатов; HTTP-контракт проверяет путь pending → подтверждённая недоступность синтетического ключа.

После истечения пятиминутного negative cache участник мог оставаться pending без задания, пока состав гильдии ещё свежий. Сводка теперь допускает одно ограниченное задание повторного обхода состава. Автоматическое задание переиспользует свежий разрешённый snapshot, не обращаясь заново к Blizzard за составом. Worker сохраняет пакеты по 50, дедупликацию, capacity и cooldown персонажей. Ручное обновление продолжает запрашивать новый состав. Отдельный PostgreSQL-тест подтверждает expiry → повторную постановку, сохранение отрицательного кеша до срока, cooldown после ошибки и ручной путь.

nginx раньше ограничивал тело 4 KiB при API social limit 8 KiB и возвращал HTML 413. Теперь тело до 16 KiB достигает собственных API-ограничений; более крупный запрос получает JSON `REQUEST_TOO_LARGE`, UUID и `no-store` от gateway. Повторяющийся `nosniff` устранён. Runtime включён в read limiter; подмена `X-Real-IP` вне доверенного proxy не создаёт новую лимитерную идентичность. Известный демонстрационный HMAC-ключ запрещён для live-источника.

## Наблюдаемость и контейнеры

Проверка миграций на startup/readiness читает полный ledger и checksum, не выполняя DDL. Она отвергает пустой, неполный, изменённый или неизвестный будущий ledger. Readiness worker дополнительно учитывает жизненный цикл всех компонентов и shutdown. Redis сохраняет допустимый degraded mode. Ошибка scrape имеет явный gauge и HTTP 503.

Все три очереди имеют агрегаты active/running/due/retry/failed, возраст due-задач и истёкшие lease. HTTP histogram использует шаблоны маршрутов с ограниченной кардинальностью. nginx больше не сохраняет raw URI. PostgreSQL error logging исключает statements/параметры и подробные payload. Docker-журналы ограничены по объёму. API/worker запускаются с read-only filesystem, сброшенными capabilities и `no-new-privileges`; healthcheck проверяет readiness.

Локальный стек Prometheus/Grafana закреплён digest, принимает подключения только с loopback и собирает обе внутренние цели. Предоставлены восемь панелей и четыре стартовых alert rules. Grafana требует пароль, анонимный доступ и автоматическая предустановка плагинов отключены. Пароль и отдельный ключ Grafana создаются в игнорируемом `.env.monitoring`; все `.env.*` исключены из Docker context. Получатели оповещений не подключены. Команды и смысл метрик — в [инструкции мониторинга](monitoring.md).

## Подтверждённые проверки

- Go tests с реальным PostgreSQL, `go vet`, `go mod verify` и Linux amd64 Race Detector пройдены. Дополнительный race-прогон покрывает последний фикс повторной постановки гильдии.
- `govulncheck@v1.9.0` в Linux-среде сборки: `No vulnerabilities found`. Оба `npm audit` — ноль известных уязвимостей. Первоначальный запрос Go scanner с Windows не получил доступ к vuln.go.dev; он не был засчитан как успешный. Сканер использует текущую базу известных уязвимостей и не заменяет аудит приложения.
- OpenAPI 3.1 версии 0.6.0 содержит 22 маршрута, включая внутренний `/metrics`. Полный HTTP-контракт прошёл: 47 реальных ответов через nginx, в том числе холодное сравнение и переопрос участников. Число ответов меняется в зависимости от прогретости кеша и фоновых заданий.
- HTTP security smoke: 16 проверок публичных API/gateway. Лимиты и 413 проверяются при 5/9/17 KiB. Внутренние health/metrics недоступны с обоих публичных origins.
- Нагрузка ограничена 8 VU и 20 секундами, с настоящим limiter. Методика, отдельные показатели 200/429 и фактические результаты — в [отчёте нагрузки](load-testing.md). Это не проверка 1000 RPS или production SLO.
- Изолированный synthetic backup/restore drill пройден: разрешённый профиль доступен, карантин/expiry скрывают payload, maintenance удаляет истёкшую идентичность. Исходная БД только читается, временная БД и dump удаляются. Подробности и локальные времена — в [recovery runbook](recovery.md).
- Prometheus config и четыре правила проверены `promtool`; обе цели имеют `up`, worker показывает три работающих компонента. Grafana API подтверждает provisioned dashboard и восемь панелей.

CI включает форматирование, целостность модулей, vet/race, vulnerability scans, web build/tests, реальные HTTP-контракты и security smoke через nginx. Actions закреплены commit SHA, права ограничены `contents:read`, есть timeout и cleanup. Удалённый CI не запускался: у репозитория пока нет remote. Dependabot настроен для Go, npm и Actions.

## Что требуется для публичного релиза

Нужны целевой сервер/домен, эксплуатационный бюджет, TLS/ingress и измерения на целевой конфигурации. Реальные credentials и обезличенные ответы Blizzard/Warcraft Logs необходимы для live-приёмки адаптеров и расчётов; актуальные игровые правила не включаются без подтверждённых источников.

Настоящее backup/restore требует off-host копий, шифрования, расписания, retention, проверенных RPO/RTO и закрытого восстановления с повторной проверкой публикации. Долговременного журнала удалений после backup сейчас нет; пятиминутные negative hashes его не заменяют. Локальный drill не открывает восстановленную базу для пользователей и не доказывает готовность live-восстановления. Публичный security-аудит, проверка образов и нагрузочная квалификация целевого сервера остаются отдельной приёмкой.
