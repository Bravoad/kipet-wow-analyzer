# Локальные нагрузочные и HTTP security-проверки

1 ноября 2026 года. Эти проверки предназначены для работающего локального fixture-окружения. Они не подтверждают live-контракты Blizzard/Warcraft Logs, production-безопасность, 1000 RPS, доступность или SLO.

## Границы и воспроизведение

Сначала запустите обычное приложение через Compose и выполните [контрактный прогон](local-development.md). Он загружает синтетические примеры. Затем выполняйте security smoke и нагрузку последовательно: они используют настоящий limiter одного клиента. Параллельный контрактный прогон, ручная работа в браузере и предыдущие запросы к этому IP влияют на начальный остаток token bucket.

```powershell
node tests/security/http-smoke.mjs
pwsh -File tests/load/run-local.ps1
```

HTTP smoke использует Node.js без сторонних пакетов. По умолчанию он проверяет nginx на `127.0.0.1:5173` и прямой API на `127.0.0.1:8080`. Переопределения `API_BASE_URL`/`API_DIRECT_BASE_URL` допускают только локальные HTTP origins, без credentials, path/query/hash. Проверка `runtime.provider_mode=fixture` выполняется до тестовых запросов.

PowerShell runner запускает официальный образ Grafana k6 1.6.1 с зафиксированным digest. Контейнер имеет read-only root filesystem, сброшенные Linux capabilities и `no-new-privileges`; скрипт примонтирован только для чтения, запись разрешена в `artifacts`. `--no-usage-report` выключает отправку анонимной статистики k6. Docker Desktop обращается к локальному origin через `host.docker.internal:5173`. Скрипт не передаёт `X-Real-IP`/`X-Forwarded-For` и не обходит лимитеры.

Допустимы от 1 до 8 VU и от 1 до 20 секунд. По умолчанию — 8 VU, 20 секунд и 3 секунды graceful stop, timeout запроса — 3 секунды. Setup проверяет fixture за максимум 8 секунд. Меньший пробный прогон:

```powershell
pwsh -File tests/load/run-local.ps1 -VUs 2 -DurationSeconds 5
```

При нативно установленном k6 можно запустить скрипт из корня репозитория:

```powershell
k6 run --no-usage-report tests/load/fixture-read.js
```

Он использует `http://127.0.0.1:5173`. Скрипт отказывается выполнять тест на внешнем origin или в live-режиме. Ограничения origin проверены отдельным запуском с `example.invalid`: оба инструмента отказываются до сетевого запроса. Сценарий использует фиксированный небольшой набор известных синтетических профилей/секций/сводки гильдии/каталога; он не создаёт случайные ключи и не запускает массовое обновление состава.

## Что измеряется

`fixture_reads_200` считает выданные ответы, `fixture_reads_202` — принятую фоновую загрузку, `fixture_reads_429` — ожидаемый отказ limiter. `unexpected_responses` считает любые другие статусы, неверные envelope/headers или некорректный `Retry-After`. Порог проверок требует ноль неожиданных ответов, хотя бы один 200 и успешные проверки каждого ответа. Полный стандартный прогон 8 VU/20 секунд также требует хотя бы один 429, чтобы отключённый limiter не выглядел успешной защитой. Порог latency не задан: эксплуатационный бюджет и целевой сервер ещё не выбраны.

Латентность 200 и 429 считается разными Trend-метриками. Быстрые 429 не улучшают median/p95 разрешённых чтений. Стандартный `http_req_failed` k6 включает 429 по умолчанию; отдельное поле `http_req_failed_rate_including_429` сохраняет этот показатель, чтобы ожидаемая защита не была выдана за ошибку сервиса или скрыта. Описание метрик — в [официальной документации k6](https://grafana.com/docs/k6/latest/using-k6/metrics/reference/), структура итогового JSON — в [документации handleSummary](https://grafana.com/docs/k6/latest/results-output/end-of-test/custom-summary/).

Краткие отчёты записываются в `artifacts/load-fixture-summary.json` и `artifacts/security-http-summary.json`. Каталог исключён из Git. Отчёты содержат только origin, параметры и агрегаты/результаты проверок; payload персонажей, секреты и сырые URL с именами туда не записываются. Повторный запуск заменяет предыдущий файл.

## HTTP security smoke

Проверяются CSP/nosniff/referrer policy и скрытие версии nginx; отсутствие доступа к `/health/live`, `/health/ready`, `/metrics` через оба публичных origin; серверный UUID запроса вместо доверия клиентскому заголовку; `no-store` и JSON envelope. Неверный регион, caller GraphQL, `force`, неизвестные JSON-поля и слишком большое тело должны давать типизированную безопасную ошибку. Проверки body size охватывают 5 KiB, больше 8 KiB и больше 16 KiB, чтобы расхождение лимитов nginx/API не превращалось в незадокументированный HTML-ответ. Limiter учитывается без подмены IP: smoke делает не более двух ограниченных ожиданий `Retry-After` и затем явно проваливает сценарий.

Проверки не выполняют сканирование интернета, подбор ключей, обход авторизации или destructive SQL. Это ограниченная регрессия внешнего HTTP-периметра. Отдельно остаются penetration testing, проверка TLS/ingress целевого хостинга, dependency/image scans и испытания реального отказа зависимостей.

## Подтверждённое локальное измерение

На финальной локальной сборке API 0.6.0 прогон в Docker Desktop с 8 VU в течение 20 секунд обработал 632 чтения: 58 ответов 200, 574 ожидаемых 429, 0 ответов 202, 0 неожиданных ошибок. Все 3160 проверок прошли, включая отдельный порог наличия 429. Для 200 median составила 6,90 ms, p95 — 22,01 ms; median 429 — 2,63 ms. Стандартный `http_req_failed` с учётом ожидаемых 429 — 0,90679; это не доля неожиданных ошибок, которых было ноль. Эти значения относятся только к этой короткой синтетической выборке и не являются гарантией. Подробности очередей и сопоставления данных проверяются обычными Go/контрактными тестами, а не этим измерением.

HTTP security smoke после обновления прошёл 16 из 16 проверок. Первоначально он обнаружил дублированный `nosniff`, публичный лимит тела 4 KiB при серверном 8 KiB и HTML 413 без `no-store`; исправления проверены повторным прогоном через nginx. Внешние health/metrics закрыты на обоих публичных origin; JSON 413 подтверждён для тела 9 KiB и 17 KiB. Удалённый CI и публичный security-аудит этим локальным результатом не считаются выполненными.
