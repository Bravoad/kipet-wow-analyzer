# Резервная копия и изолированная проверка восстановления

1 ноября 2026 года. Это локальный synthetic drill и порядок подготовки восстановления. Он не означает настроенное резервное копирование production, согласованные RPO/RTO или наличие журнала удалений.

## Воспроизводимый локальный drill

Нужны PowerShell 7+, Docker Compose, работающий сервис PostgreSQL и Go из [локальной инструкции](local-development.md). В приложении сначала откройте хотя бы один демопрофиль; для проверки всех модулей откройте также демогильдию и боевой отчёт.

Из корня проекта выполните:

```powershell
pwsh -NoProfile -File deploy/operations/recovery-drill.ps1
```

Скрипт принимает `-SourceDatabase kipet` и `-PostgresPort 5432` для локального Compose. Обе записи `provider_mode` и `combat_provider_mode` должны явно равняться `fixture`. Непомеченная или настоящая база отвергается до создания архива. Скрипт только читает исходную БД и не останавливает API/worker.

Порядок проверки:

1. Создать custom-format `pg_dump` без владельцев и ACL. Бинарный файл копируется через Docker Compose, без текстового PowerShell pipeline.
2. Создать новую БД со случайным именем `kipet_recovery_drill_<16 hex>`; существующее имя не переиспользуется. Восстановить архив через `pg_restore --exit-on-error`.
3. Сравнить количество записей migration ledger с источником и проверить checksums миграций приложением. Добавить случайный guard token только в восстановленную БД.
4. Запустить [recoverycheck](../../deploy/operations/recoverycheck/main.go). Он принимает только loopback-адрес, строгое тестовое имя, фиксированный `sslmode=disable` без параметров переадресации и совпадающий guard token в БД. API/worker для восстановленной копии не запускаются; внешних запросов к провайдерам нет.
5. Через настоящий batch repository и публикационную проекцию проверить доступный восстановленный профиль. Внутри тестовой копии выставить карантин, затем просрочить identity deadline и убедиться, что payload скрыт. Выполнить maintenance персонажей/боевых отчётов/гильдий и проверить удаление просроченной идентичности.
6. Закрыть соединения, удалить только БД с точным сгенерированным именем и проверить её отсутствие. `DROP DATABASE` не использует FORCE: неожиданное соединение приводит к ошибке, а не к остановке другого процесса. Удалить временный архив в контейнере и локальную копию.

Результат — JSON в `artifacts/recovery/<run_id>.json`: timestamps UTC, размер и SHA-256 архива, времена backup/restore+verify, количество восстановленных записей и результаты публикационных проверок. В нём нет URL подключения, имён персонажей, payload или токена. `artifacts/` уже исключён из Git. По умолчанию dump удаляется и после ошибки; `-KeepArchive` сохраняет только эту синтетическую копию для разбора. Сохранённый dump удаляйте вручную после разбора и не помещайте в Git.

Не используйте этот скрипт как универсальную команду восстановления live-БД. Его ограничение `fixture` намеренное. Аварийное завершение самого PowerShell/контейнера может оставить тестовую БД или архив: точное имя выводится из `run_id` отчёта. Перед ручным удалением проверьте имя, отсутствие подключённых API/worker и guard token; не применяйте wildcard/массовое удаление баз.

## Что означает измеренное время

`backup_ms` включает проверки, dump и копирование; `restore_verify_ms` включает создание проверочного процесса Go, возможную компиляцию и публикационные проверки. Это локальное время конкретного небольшого synthetic набора. Оно не является гарантией RTO для целевого сервера. PostgreSQL dump согласован на момент своего snapshot; без WAL-архива нет восстановления на произвольный момент. Фактическая потеря данных зависит от расписания успешных копий, которое пока не настроено. Нужные RPO/RTO, объём базы и бюджет выбираются перед публичным запуском.

## Восстановление настоящих данных перед открытием сервиса

Восстанавливайте только в новую изолированную БД, без публичного ingress и без подключённых API/worker. Используйте пустой Redis: кеш и состояние лимитеров не являются авторитетной резервной копией. До выдачи данных нужны совместимая версия приложения, успешная проверка ledger/checksums, правильные source markers и сохранённые исходные deadlines. Восстановление не обновляет `fetched_at`, `fresh_until`, `valid_until` или время проверки публичности.

После восстановления сначала выполните очистку истёкших данных через штатные maintenance-пути. Сохраняйте карантинные флаги из копии. Любой восстановленный профиль/состав/боевой отчёт, чья текущая доступность неизвестна, должен оставаться закрытым до новой проверки источника. Операционный порядок — пометить восстановленные идентичности публикационно заблокированными в изолированной БД, аннулировать восстановленные активные задания/lease и начать новые задания проверки источника. Старые задания гильдии с сохранённым snapshot/cursor не заменяют новую проверку состава. Для персонажей используется пара `publication_blocked_at` / `publication_block_reason='provider_access_denied'`, для гильдий и отчётов — `blocked_at`. Затем допускаются только успешно перепроверенные ресурсы. Это операционный карантин; успешный штатный worker снимает его только после подтверждённого ответа источника. Не снимайте блокировку массовым UPDATE ради запуска. Этот порядок требует отдельного проверенного операционного инструмента для live-восстановления; локальный drill его не автоматизирует.

В текущей реализации **нет долговременного журнала удалений после даты backup**. Пятиминутные negative HMAC-записи не заменяют такой журнал и не позволяют восстановить полный список удалений. Поэтому копия может содержать профиль, который после неё был удалён или стал закрытым. Простой запуск восстановленной базы с пустым Redis не решает эту проблему. Без независимого журнала удалений безопасный путь — закрытая восстановленная база и повторная проверка каждого публикуемого ресурса; неподтверждённые данные не открываются. Полное восстановление такого типа ещё не автоматизировано и не проверено live.

Перед production нужны отдельные решения: шифрование backup, доступ оператора и ключей, off-host копии, срок хранения не дольше принятой политики источника, расписание, мониторинг неуспеха, проверяемое удаление старых копий и учёт удалений при восстановлении. Нельзя обещать немедленное исчезновение записи из уже созданного неизменяемого архива. Копии имеют собственный ограниченный retention и остаются offline; открываемая восстановленная база повторно проходит ограничения публикации. При смене HMAC-ключа старые negative hashes не работают как текущий deny-list — повторная проверка источника обязательна.

## Локальный результат

1 ноября 2026 synthetic drill завершён: в последнем прогоне восстановлены 3 персонажа, 18 снимков, 2 снимка гильдии и 1 боевой отчёт; ledger содержит 8 миграций. Разрешённый профиль доступен, карантин и истечение срока скрывают payload, maintenance удаляет просроченную идентичность. Тестовая БД и оба временных dump-файла удалены. Проверка helper также отвергает обычную БД `kipet`, внешние hosts и URL-параметры, способные поменять целевую БД/host. Backup занял 1254 мс, restore с проверками — 2601 мс; это измерение небольшой локальной копии. SHA-256 и полный результат находятся в локальном JSON-отчёте; вывод не содержит игровых payload.
